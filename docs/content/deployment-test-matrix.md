# Deployment behavior-to-test contract (#4305)

Written before implementation. Risk is **high**: infrastructure lifecycle,
database mutation/recovery, RBAC/secret boundaries, and a published deployment
interface. The contract is [maintenance-only v1](deployment.md).

Every row has the ten required design fields. Commands name executable test
entrypoints; the integration ledger below distinguishes completed evidence from
required qualification. A `PENDING:` downstream rollout needs separate target
authorization and is not claimed complete. Rendering proves manifest behavior only. Mock observations
cannot replace the disposable controller/database exercise or real rollout.

In the table, `PG` means the initial deployed PostgreSQL boundary (14+ under the
existing permission contract). The controller feature floor is helm-controller
1.4.5 with matching CRDs; record actual tested versions for each qualification. SQLite/DuckDB/PGlite are not deployed chart targets. A public
core API supporting those dialects needs its own package matrix across every
declared supported dialect before shipping.

## Qualification evidence

This matrix was drafted before implementation. Record current results alongside
an exact reviewed revision in the PR and retained validation artifacts, including:

- Helm schema/render/packaging and runner contracts, including local Git races.
- Real PostgreSQL durable-step and role-boundary tests, including interruption.
- The isolated Flux/Kubernetes/Ingress/PostgreSQL/S3 exercise, its tool/controller
  versions, sentinel retention, failure/resume and cleanup outcomes.
- The required touched-package/root validation and independent high-risk review.

The exercise uses synthetic applications and test-only HelmRelease changes.
It does not prove protected Git publication in a real cluster, downstream wrapper
adoption, production writer fencing, or a real downstream rollout. Those require
reviewed downstream changes and explicit target/environment authorization. Keep
#4305 open until its actual adoption and rollout criteria have evidence.

Run focused package checks first and include focused deployment commands in normal
validation. Full validation follows root `AGENTS.md` and `TESTING_STANDARD.md`;
heavy work uses the prescribed cluster-test workflow. The integration owner must
record disposable teardown even on failure. Do not replace failed documented
commands with a different toolchain and report green.

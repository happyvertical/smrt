# smrt-core/change signals / live events

Module semantics for `src/change-signals.ts` + the generated `_events` SSE route. Package orientation, the cross-module
invariants, and the traps that apply before editing anything live in
[../AGENTS.md](../AGENTS.md) — read that first.

## Live Events / Change Signals (#1763, server half)

The push companion to the change feed (`src/change-signals.ts` + the generated `_events` SSE route) — the server half of live cache invalidation (PRD #1755). The client subscriber (two-client/reconnect/polling-fallback ACs) is a separate later slice.

- **Change-signal bus** (`src/change-signals.ts`): every framework save/delete that appends a durable feed row also publishes a coarse `ChangeSignal` `{ table, operation, rowId, tenantId, seq }` — **never a row payload** (authorization stays on the read path). Structurally mirrors the collection cache's notify/listen path. `subscribeToChangeSignals(db, listener) → unsubscribe`; `publishChangeSignal`/`broadcastChangeSignal`/the listener loop stay internal. `appendChange` now returns the allocated `seq` (was `void`); the signal carries it as a coarse resume cursor (`bumpChangeFeed` ignores the return). The publish runs only after the append SUCCEEDS (no signal without a durable feed row) and in its own log-and-swallow try/catch, so a signal problem never fails the user's write. `_smrt_*` writes never signal (the writer skips them). Delivery is synchronous per-listener with per-listener try/catch (one throwing SSE controller never blocks others); no per-subscriber queue — backpressure rides the platform `ReadableStream`.
- **In-process + cross-replica**: locally-published and peer-received signals go through the SAME `deliverLocally` path. Cross-replica fan-out rides the db adapter's optional notification capability (`db.notifications`, a NEW `smrt_change_signals` channel distinct from the cache channel) with echo-avoidance by `PROCESS_ID`. No capability → in-process only, warn-once, **never an error, never blocks the write** (subscribers on other replicas fall back to cursor polling).
- **Generated `_events` SSE route**: REST (`GET {basePath}/_events`, requires `authMiddleware`, otherwise 401 — fail-closed, per-model `api.public` does NOT apply; 405 non-GET; 503 no db or subscriber capacity reached) and SvelteKit (`{routesDir}/_events/+server.ts`, requires an authenticated principal on `locals`; opt out via `sveltekit.eventsRoute.enabled: false`; cap via `sveltekit.eventsRoute.maxSubscribers`, where `0` means unlimited). Tenant scope is captured ONCE at connection open (`resolveDispatchTenantScope`) and filtered server-side per signal via `signalVisibleToTenant` (same rule as `getChangesSince`'s tenant filter) before any byte hits the wire — delivery runs outside any tenant ALS context, so it must use the captured value. The stream lifecycle lives in `buildChangeEventStream(db, { cursor, tenantScope, heartbeatMs?, manifestHash?, locals? })` (exported; the SvelteKit route imports it so it stays thin, and one fix covers both transports): `retry: 3000`, optional connection-open `event: manifest` carrying `{ manifestHash }` for live contract detection, ordered delivery from a per-connection cursor (below), heartbeat (`DEFAULT_EVENTS_HEARTBEAT_MS` = 15s), and `cancel()` teardown (clears timers + unsubscribes). **Ordered delivery invariant**: every `change` frame comes from a read of the durable feed after the connection's own sent cursor, in sequence order; a live signal is only a wake-up that triggers that read. The stream therefore never frames a sequence at or below one it already sent, and never frames one while an earlier committed sequence it may see is still unsent — the `Last-Event-ID` a client resumes from always covers everything before it, including across a multi-page catch-up during which writes keep landing. The stream subscribes first, then fixes its starting cursor (`Last-Event-ID` header beats `?since=`; default = live-forward only, starting at the feed head), then reads forward until the feed is exhausted; `resyncRequired` → `event: resync` at the fresh horizon, and delivery continues from it. Filters use the CAPTURED tenant scope (not re-resolved from ALS) and the captured table/row authorization, applied in memory to an unfiltered page; rows a connection may not see still advance its cursor. Identical in-flight page reads (same database, cursor and drain mode) are shared, so one write wakes every caught-up connection onto one query. A read that fails **closes** the stream rather than continuing live-only: the client reconnects from the last id it received and the server replays from there. A wake-up that names a sequence the reader cannot see yet (a writer whose commit is not visible on this connection) is re-read once after 250 ms and then on each heartbeat until the feed reaches it. SSE change frame: `id: <seq>\nevent: change\ndata: {table,operation,rowId,tenantId}\n\n` — seq is ONLY in the `id:` line, never the data JSON. Subscriber cap default is `DEFAULT_EVENTS_MAX_SUBSCRIBERS` = 1000; over-cap connections return retryable 503 + `Retry-After`, and existing subscribers are unaffected. A second cap applies per principal (`DEFAULT_EVENTS_MAX_SUBSCRIBERS_PER_PRINCIPAL` = 16 per process; `maxSubscribersPerPrincipal` on `handleEventsRoute`, `0` disables): `tryReserveChangeEventSubscriberSlot(db, maxSubscribers, { locals, request })` identifies the principal by `resolveChangeEventPrincipalKey()` — `locals.user.id`, then `locals.session.userId`/`.id`, then a SHA-256 digest of the request's `Authorization`, then of its `Cookie` header (synchronous `utils/sha256.ts`; the raw credential is never a key) — and holds that slot until the stream tears down; a request nothing identifies is bounded by the process cap only. The generated SvelteKit route passes `{ locals, request }`; REST passes the `authMiddleware`-processed request. Neither `sveltekit.eventsRoute` nor the REST generator config exposes the per-principal cap or lifetime yet, so generated routes use the defaults. **Bounded buffering**: the stream's queue has a 64-chunk high-water mark and the connection reads the feed only when `pull()` reports room, so a client that stops reading costs at most that plus one feed page — live writes only raise a sequence number — and heartbeats are skipped while it is not draining. **Bounded lifetime**: a stream ends after `DEFAULT_EVENTS_MAX_CONNECTION_MS` (10 minutes, minus up to 10% jitter; `maxConnectionMs`, `0` = unlimited); `EventSource` reconnects with its `Last-Event-ID`, re-running authentication and re-capturing tenant scope and table authorization, so a revoked session stops receiving within that bound. Every timer is cleared on teardown, and none is armed by a `start()` that finds the stream already cancelled. **Cross-origin is opt-in and fail-closed (#1861)**: same-origin only by default. REST wraps `_events` in its CORS layer — set `enableCors` + an explicit `allowedOrigins` allowlist + `allowCredentials: true` and an allow-listed browser can subscribe with a credentialed `EventSource` (`withCredentials: true`); the response echoes the specific `Origin` (never `*`) plus `Access-Control-Allow-Credentials: true`. SvelteKit mirrors this via `sveltekit.eventsRoute.allowedOrigins` + `allowCredentials` (the generated route bakes the allowlist into a `Set`, echoes only a member origin, and answers a credentialed `OPTIONS` preflight). CORS never authorizes — the fail-closed auth guard and captured tenant scope are unchanged, so the read posture holds identically across origins; it only lets an allow-listed browser's cookies reach the guard. Client disconnect through the Node `createServer` bridge now cancels the response reader (was a teardown leak) so `cancel()` fires and the subscription is released.
- **Table/row authorization** (#3020, `change-feed-authz.ts`), evaluated on BOTH transports: the SvelteKit route forwards `{ locals, request }` and REST's `handleEventsRoute` forwards `{ locals: undefined, request: authResult }` (the `authMiddleware`-processed request — REST has no `locals`, so a hook a REST-hosting consumer registers identifies the principal from `request`) into `buildChangeEventStream`. If the consumer registered `authorizeChangeFeed`/`isChangeFeedEntryVisible`, `start()` resolves the allowed-tables set ONCE at connection open — same reasoning and same code shape as captured `tenantScope` — and applies both hooks to every page the connection reads, catch-up and live alike (an empty allow-list — `isChangeFeedDenyAll()`, the same call `change-feed-authz.ts`'s own `readAuthorized()` makes; see `change-feed.md`'s #3020 section — frames nothing while the cursor still advances). Table checks are synchronous (a `Set.has`); the row-visibility check is async and runs inside the connection's single ordered read loop, so no per-signal promise chain exists. The stream subscribes and fixes its starting cursor (the supplied one, or the feed head) BEFORE the authorizer `await`, so a write that commits while a hook is pending is still read once the allow-list resolves — including on a live-forward-only connection. `start()` re-checks `closed` after that `await` and stops when the client disconnected meanwhile (#3020 P2); `cancel()` already unsubscribed and released the slot.
- **Known gaps** (documented in the module): raw-SQL writes don't signal (same gap as the feed); live signals for caller-managed-transaction writes are best-effort (the append + signal fire pre-commit, so a rolled-back write may emit a signal and its freed seq is later reused) — the autocommit default path is exact. The `_events` stream is not affected by such a signal: it frames only what its feed read returns, so a wake-up for a rolled-back sequence frames nothing.

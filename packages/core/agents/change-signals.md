# smrt-core/change signals / live events

Module semantics for `src/change-signals.ts` + the generated `_events` SSE route. Package orientation, the cross-module
invariants, and the traps that apply before editing anything live in
[../AGENTS.md](../AGENTS.md) — read that first.

## Live Events / Change Signals (#1763, server half)

The push companion to the change feed (`src/change-signals.ts` + the generated `_events` SSE route) — the server half of live cache invalidation (PRD #1755). The client subscriber (two-client/reconnect/polling-fallback ACs) is a separate later slice.

- **Change-signal bus** (`src/change-signals.ts`): every framework save/delete that appends a durable feed row also publishes a coarse `ChangeSignal` `{ table, operation, rowId, tenantId, seq }` — **never a row payload** (authorization stays on the read path). Structurally mirrors the collection cache's notify/listen path. Signal scope follows the database's identity (`resolveDbCacheKey`: `db.url`, or `db.config.url` for a handle exposing only that), except that a per-connection in-memory database — detected on that same effective URL — is private to its handle even when another handle shares its URL, so its signals never reach another database's subscribers. A signal with a feed sequence is a wake-up and reaches every subscriber of the scope (each re-reads its own feed). A signal with **no** feed sequence is delivered only to subscribers whose feed identity (`databaseReadScope`: the URL of a shared embedded database, otherwise the handle — every PostgreSQL handle, since one URL can serve several schemas) is the publisher's; a peer-received one names no schema or handle, so it reaches only subscribers whose identity is the shared URL itself, never a PostgreSQL subscriber. Framework writes always carry a sequence, so this only narrows foreign or legacy producers. `subscribeToChangeSignals(db, listener) → unsubscribe` (a listener is registered once per scope: subscribing it again adds only that database's feed identity, so it is still invoked once per signal, holds one subscriber slot, and any of its unsubscribe functions removes it); `publishChangeSignal`/`broadcastChangeSignal`/the listener loop stay internal. `appendChange` now returns the allocated `seq` (was `void`); the signal carries it as a coarse resume cursor (`bumpChangeFeed` ignores the return). The publish runs only after the append SUCCEEDS (no signal without a durable feed row) and in its own log-and-swallow try/catch, so a signal problem never fails the user's write. `_smrt_*` writes never signal (the writer skips them). Delivery is synchronous per-listener with per-listener try/catch (one throwing SSE controller never blocks others); no per-subscriber queue — backpressure rides the platform `ReadableStream`.
- **In-process + cross-replica**: locally-published and peer-received signals go through the SAME `deliverLocally` path. Cross-replica fan-out rides the db adapter's optional notification capability (`db.notifications`, a NEW `smrt_change_signals` channel distinct from the cache channel) with echo-avoidance by `PROCESS_ID`. No capability → in-process only, warn-once, **never an error, never blocks the write** (subscribers on other replicas fall back to cursor polling).
- **Generated `_events` SSE route**: REST (`GET {basePath}/_events`, requires `authMiddleware`, otherwise 401 — fail-closed, per-model `api.public` does NOT apply; 405 non-GET; 503 no db or subscriber capacity reached) and SvelteKit (`{routesDir}/_events/+server.ts`, requires an authenticated principal on `locals`; opt out via `sveltekit.eventsRoute.enabled: false`; cap via `sveltekit.eventsRoute.maxSubscribers`, where `0` means unlimited). Tenant scope is captured ONCE at connection open (`resolveDispatchTenantScope`) and filtered server-side per signal via `signalVisibleToTenant` (same rule as `getChangesSince`'s tenant filter) before any byte hits the wire — delivery runs outside any tenant ALS context, so it must use the captured value. The stream lifecycle lives in `buildChangeEventStream(db, { cursor, tenantScope, heartbeatMs?, manifestHash?, locals? })` (exported; the SvelteKit route imports it so it stays thin, and one fix covers both transports): `retry: 3000`, optional connection-open `event: manifest` carrying `{ manifestHash }` for live contract detection, ordered delivery from a per-connection cursor (below), heartbeat (`DEFAULT_EVENTS_HEARTBEAT_MS` = 15s), and `cancel()` teardown (clears timers + unsubscribes). **Ordered delivery invariant**: every `change` frame comes from a read of the durable feed after the connection's own sent cursor, in sequence order; a live signal is only a wake-up that triggers that read. The stream therefore never frames a sequence at or below one it already sent, and never frames one while an earlier committed sequence it may see is still unsent — the `Last-Event-ID` a client resumes from always covers everything before it, including across a multi-page catch-up during which writes keep landing. The stream subscribes first, then fixes its starting cursor (`Last-Event-ID` header beats `?since=`; default = live-forward only, starting at the feed head), then reads forward until the feed is exhausted; `resyncRequired` → `event: resync` at the fresh horizon, and delivery continues from it. Filters use the CAPTURED tenant scope (not re-resolved from ALS) and the captured table/row authorization, applied in memory to an unfiltered page; rows a connection may not see still advance its cursor. Identical in-flight page reads (same database, cursor and drain mode) are shared, so one write wakes every caught-up connection onto one query; "same database" is `databaseReadScope`: the URL for a shared embedded database, but the handle itself for a per-connection in-memory database (`:memory:`, `file::memory:`, `memory://…`) and for every PostgreSQL handle (two pools on one URL can run sessions that see different schemas), so a page is only ever shared between connections proven to read the same feed. A read still waiting in the write queue is skipped when it reaches the front if every connection that asked for it has disconnected, so client churn behind a long transaction leaves no queued database work. Reads go through `getChangesSince`, which on embedded engines waits for any open framework write transaction (it holds the write queue), and the read loop runs detached from the waking caller's write context (`runOutsideWriteContext`), so a wake-up delivered from a commit callback cannot make later reads re-entrant: a stream never frames a sequence an uncommitted framework transaction holds. A read that fails **closes** the stream rather than continuing live-only: the client reconnects from the last id it received and the server replays from there. A wake-up that names a sequence the reader cannot see yet (a writer whose commit is not visible on this connection) is re-read once after 250 ms. Independently of signals, every idle heartbeat runs one exhaustive read (shared with identical reads in flight; it also sequences staged PostgreSQL work), so a change committed with no signal reaching this process — another replica without a notification channel, a lost notification — is delivered within one heartbeat interval. A signal that carries **no feed sequence** (`seq` not a positive integer — a producer that writes no feed row) is framed directly, as before the ordered read existed, under the same tenant/table/row filters, but with **no `id:` line**, so the client's resume cursor is not moved to a value the feed never assigned. It is best-effort: dropped until the connection's table authorization has settled (an unsequenced signal has no later feed read that would apply it), dropped while the reader is not draining, and — with an asynchronous row hook — dropped before the hook is asked once 16 checks are outstanding on the connection. Reading a stream inside a framework write transaction on the same embedded database errors with a clear message at that read: its feed reads wait for that transaction, so a reader awaiting a frame there would deadlock it and every writer queued behind it. The check runs when the reader asks for data (the returned stream pulls from the inner one only on demand) and looks only at holds that are still live (`holdsWriteQueue`), so building a stream inside a transaction and reading it after commit works, as does a callback scheduled during a transaction but run after it. On a PostgreSQL-dialect database (PostgreSQL or PGlite), `buildChangeEventStream` refuses a framework transaction's handle with a clear error, releasing the caller's subscriber slot: the stream reads through the root, whose sessions do not carry the transaction's `search_path`, role or other session settings, so it could serve another schema's feed. Build the stream from the root database, outside the transaction. All of `start()`'s feed reads, including the live-forward head read, run detached from the caller's write context. The live-forward start position never sits past a change signalled after subscribing: the earliest sequence signalled before the head was sampled lowers the start cursor to just before it. SSE change frame: `id: <seq>\nevent: change\ndata: {table,operation,rowId,tenantId}\n\n` — seq is ONLY in the `id:` line, never the data JSON. Subscriber cap default is `DEFAULT_EVENTS_MAX_SUBSCRIBERS` = 1000; over-cap connections return retryable 503 + `Retry-After`, and existing subscribers are unaffected. **Bounded buffering**: the stream's queue has a 64-chunk high-water mark and the connection reads the feed only when `pull()` reports room, so a client that stops reading costs at most that plus one feed page — live writes only raise a sequence number — and heartbeats are skipped while it is not draining. Every timer is cleared on teardown, and none is armed by a `start()` that finds the stream already cancelled. **Cross-origin is opt-in and fail-closed (#1861)**: same-origin only by default. REST wraps `_events` in its CORS layer — set `enableCors` + an explicit `allowedOrigins` allowlist + `allowCredentials: true` and an allow-listed browser can subscribe with a credentialed `EventSource` (`withCredentials: true`); the response echoes the specific `Origin` (never `*`) plus `Access-Control-Allow-Credentials: true`. SvelteKit mirrors this via `sveltekit.eventsRoute.allowedOrigins` + `allowCredentials` (the generated route bakes the allowlist into a `Set`, echoes only a member origin, and answers a credentialed `OPTIONS` preflight). CORS never authorizes — the fail-closed auth guard and captured tenant scope are unchanged, so the read posture holds identically across origins; it only lets an allow-listed browser's cookies reach the guard. Client disconnect through the Node `createServer` bridge now cancels the response reader (was a teardown leak) so `cancel()` fires and the subscription is released.
- **Table/row authorization** (#3020, `change-feed-authz.ts`), evaluated on BOTH transports: the SvelteKit route forwards `{ locals, request }` and REST's `handleEventsRoute` forwards `{ locals: undefined, request: authResult }` (the `authMiddleware`-processed request — REST has no `locals`, so a hook a REST-hosting consumer registers identifies the principal from `request`) into `buildChangeEventStream`. If the consumer registered `authorizeChangeFeed`/`isChangeFeedEntryVisible`, `start()` resolves the allowed-tables set ONCE at connection open — same reasoning and same code shape as captured `tenantScope` — and applies both hooks to every page the connection reads, catch-up and live alike (an empty allow-list — `isChangeFeedDenyAll()`, the same call `change-feed-authz.ts`'s own `readAuthorized()` makes; see `change-feed.md`'s #3020 section — frames nothing while the cursor still advances). Table checks are synchronous (a `Set.has`); the row-visibility check is async and runs inside the connection's single ordered read loop, so no per-signal promise chain exists. The stream subscribes and fixes its starting cursor (the supplied one, or the feed head) BEFORE the authorizer `await`, so a write that commits while a hook is pending is still read once the allow-list resolves — including on a live-forward-only connection. `start()` re-checks `closed` after that `await` and stops when the client disconnected meanwhile (#3020 P2); `cancel()` already unsubscribed and released the slot.
- **Signals follow the commit**: a write made on a framework transaction's handle — or, on local SQLite and DuckDB, whose root connection runs the transaction, a write through the root handle (a root-bound object or collection) inside the transaction's callback — (`withEmbeddedWriteTransaction` — `SmrtObject.withTransaction()`, audited collection mutations, write-through, `createMany`) hands its signals to that transaction via `deferUntilFrameworkCommit()` (`src/embedded-write-queue.ts`); they publish, in order and against the root database, after the outermost framework transaction commits, and are dropped on rollback. This matters on SQLite and DuckDB, which sequence the append inside the transaction (a rollback frees the sequence for the next write, and a client that dedupes by sequence would drop the real change), and on PostgreSQL for an append that is its transaction's first statement; PostgreSQL appends after the transaction's first write are staged and signal at drain time (#2649).
- **Known gaps** (documented in the module): raw-SQL writes don't signal (same gap as the feed); writes inside a transaction the framework does not manage (a raw `db.transaction()` or a `withCallerOwnedDatabaseTransaction` scope) still signal before commit, and a host without async-context propagation (a browser) cannot see the transaction and signals immediately. The `_events` stream frames only what its feed read returns, so such a wake-up frames nothing unless the reading connection can see the row. Also open: a write through an outer transaction's handle inside a nested framework transaction attaches its signal to the outer frame, so a rolled-back inner savepoint still publishes it at the outer commit; behind a long embedded transaction, the waiting reads of disconnected streams (page reads, and the live-forward head read) stay queued until they reach the front; a notification for an older sequence that arrives between subscribing and the head sample lowers a live-forward start into retained history; a connection that joins a shared read just as its last other reader cancels gets `null` and waits for the next signal or heartbeat; and the deadlock guard does not catch a stream read started before a transaction and awaited inside it.

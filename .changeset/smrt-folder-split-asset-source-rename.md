R3-D — split `Folder` onto its own table and rename
`Asset.parentId` → `Asset.sourceAssetId`.

**Why this matters.** Before this PR the `assets.parent_id` column did
double duty: structural hierarchy for `Folder` rows (folders are
hierarchical containers — Documents folder → Q3 reports → Drafts), and
derivation pointer for every other asset (this thumbnail came from that
photo, this transcode came from that video). Two unrelated semantics on
one column made the model harder to reason about and prevented `Folder`
from joining the `parentId` convention established by R3-A
(SmrtHierarchical: Place, Event, Account, Zone, Tag). R3-D separates the
two:

- `Folder` becomes a top-level `SmrtHierarchical` model with its own
  `folders` table. It inherits `parentId` (UUID, nullable, self-ref) and
  the framework's batched traversal helpers (`getParent`, `getChildren`,
  `getAncestors`, `getDescendants`, `getHierarchy`, `moveTo`).
- `Asset.parentId` is renamed to `Asset.sourceAssetId`. The corresponding
  methods rename too: `Asset.getParent` → `Asset.getSource`,
  `Asset.getChildren` → `Asset.getDerivatives`. The column becomes
  `assets.source_asset_id`.

After this PR, "parentId" means exactly one thing in the framework
(structural hierarchy on `SmrtHierarchical`) and derivation chains use
descriptive names per the precedent locked in R3-C
(`Fact.previousFactId`).

**API renames (smrt-assets, breaking):**

- `Asset.parentId` → `Asset.sourceAssetId`
- `Asset.getParent()` → `Asset.getSource()`
- `Asset.getChildren()` → `Asset.getDerivatives()`
- `AssetCollection.getChildren(parentId)` →
  `AssetCollection.getDerivatives(sourceAssetId)`
- `AssetOptions.parentId` → `AssetOptions.sourceAssetId`
- `StoreOptions.parentId` → `StoreOptions.sourceAssetId`
- `StoreDerivedAssetOptions extends Omit<StoreOptions, 'parentId'>` →
  `Omit<StoreOptions, 'sourceAssetId'>`

`Folder` no longer extends `Asset`. It's its own SmrtHierarchical model
with `name`, `slug` (inherited), `description`, `parentId`,
`ownerProfileId`, plus tenant scoping and timestamps. `FolderOptions`
no longer extends `AssetOptions`.

`FolderCollection.getTree(rootId?)` and `getPath(folderId)` keep their
existing signatures but now delegate to `SmrtHierarchical.getDescendants`
and `getAncestors` internally — same external behaviour, cycle-safe BFS
under the hood instead of the previous per-level recursion.

`AssetTypeCollection.initializeCommonTypes()` no longer creates a
`'folder'` AssetType row (folders aren't assets anymore).

**Cross-package consumers updated in this PR:**

- `smrt-images` — `ImageEditor.createDerivative` and `ImageDeriver.derive`
  now write `sourceAssetId` on derived `Image` rows.
- `smrt-content` — `routes/api/v1/images/[id]/edit/+server.ts` writes
  `sourceAssetId` on the derived variation. (Independent of the `fact.parentId`
  → `fact.previousFactId` rename shipped in R3-C.)
- `smrt-assets-local` — extraction-status variant tests assert on
  `asset.sourceAssetId` (was `asset.parentId`).
- `smrt-assets-ergot` — adapter-internal: `ErgotAssetSummary.parentId`
  is left as-is (it's the Ergot service's wire shape, not our column),
  documented as such.

**Schema migration (consumers must run alongside the upgrade):**

Single SQLite/Postgres migration, four steps. Run as one transaction.

```sql
-- 1. Create the `folders` table. Column set mirrors Folder's fields
--    (id PK + slug + context from SmrtObject — `context` is the
--    scope key for slug-based lookups; parent_id from
--    SmrtHierarchical; plus name/description/owner_profile_id/
--    tenant_id and timestamps). Generated by the SMRT schema
--    generator on first DB op; this DDL is here for explicit
--    migration ordering.
CREATE TABLE folders (
  id TEXT PRIMARY KEY NOT NULL,
  slug TEXT NOT NULL,
  context TEXT NOT NULL DEFAULT '',
  created_at TIMESTAMP NOT NULL DEFAULT current_timestamp,
  updated_at TIMESTAMP NOT NULL DEFAULT current_timestamp,
  parent_id TEXT,
  tenant_id TEXT,
  name TEXT,
  description TEXT,
  owner_profile_id TEXT
);
-- Unique slug+context constraint matches FolderCollection.get(slug)
-- semantics. Drop and recreate if your downstream uses a different
-- partition than the default '' context.
CREATE UNIQUE INDEX folders_slug_context_idx ON folders (slug, context);

-- 2. Copy existing folder rows out of `assets` and into `folders`,
--    preserving id (so any `assets.folder_id` references stay valid)
--    and parent_id (the existing structural-hierarchy edge between
--    folders, which becomes Folder.parentId via SmrtHierarchical).
--    `assets` does not carry a `context` column, so default to ''
--    — adjust if your deployment scoped folders by tenant or some
--    other partition.
INSERT INTO folders (id, slug, context, created_at, updated_at, parent_id, tenant_id, name, description, owner_profile_id)
SELECT id, slug, '', created_at, updated_at, parent_id, tenant_id, name, description, owner_profile_id
  FROM assets
 WHERE type_slug = 'folder';

-- 3. Rename `assets.parent_id` semantics to `source_asset_id`. For
--    non-folder rows the old column was always a derivation pointer,
--    so copy values across before dropping the old column.
ALTER TABLE assets ADD COLUMN source_asset_id TEXT;
UPDATE assets
   SET source_asset_id = parent_id
 WHERE type_slug != 'folder'
   AND parent_id IS NOT NULL
   AND parent_id != '';

-- 4. Drop the folder rows (now in `folders`) and the old column.
DELETE FROM assets WHERE type_slug = 'folder';
ALTER TABLE assets DROP COLUMN parent_id;
-- Optional cleanup: remove the now-unused 'folder' AssetType row.
DELETE FROM asset_types WHERE slug = 'folder';
```

Adapt column types and constraints to your DB if you've added indexes
or foreign keys on `assets.parent_id` — you'll need to drop them before
step 4 and recreate equivalents on `source_asset_id` and/or
`folders.parent_id`.

**Phase B (deferred, gated on user signal):** ergot.io and anytown.ai
call sites that reference `asset.parentId`, `asset.getParent()`,
`asset.getChildren()`, or filter assets by `typeSlug='folder'` will
need a codemod when the user signals readiness. The in-monorepo
`smrt-assets-ergot` adapter is updated in this PR (only internal — the
externally-shaped `ErgotAssetSummary.parentId` is preserved for wire
compatibility with the upstream Ergot service).

R3-D is the final renaming step in the R3 series. After R3-A/B/C/D
merge, the framework's vocabulary for parent-shaped self-references is
consistent: `parentId` always means structural hierarchy
(SmrtHierarchical), other self-references use descriptive names
(`Fact.previousFactId`, `Asset.sourceAssetId`).

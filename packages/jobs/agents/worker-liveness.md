# Off-loop worker liveness ticker (#1474, #4978)

**Off-loop ticker** (`worker-liveness-ticker.ts` + `worker-liveness-thread.ts`): `start()` spawns a `node:worker_threads` ticker that renews the lease on its own thread, so a CPU-bound synchronous handler on the main loop can't starve it, but only when a second connection on the **same engine** as the runtime's is available (`planLivenessConnection()`, #4978). PostgreSQL: the thread builds its own `max: 1` pool from the URL, as before. File-backed SQLite: the thread opens `db.reopenOptions()` (never `{ url, type }`), checks that its connection's `engine` equals the engine the runner reported (`db.engine`), and applies `PRAGMA busy_timeout` itself (a reopened connection inherits no PRAGMAs; `SQLITE_BUSY_TIMEOUT_MS` from `@happyvertical/smrt-core`, the same 5000 the local runtime uses; `synchronous` already defaults to FULL on both engines). `start()` sets the runner connection's timeout only when none is set, so a shared collection connection keeps its shorter 250 ms main-thread wait. `node:sqlite` and `@libsql/client` are two copies of SQLite whose file locks do not coordinate, so a thread on the other engine corrupts the WAL file when a renewal lands inside a main-thread write transaction. **When no safe same-engine connection exists** (`db.engine` undefined, as on a wrapped/proxied connection or a test double; `reopenOptions` missing or throwing `ReopenNotSupportedError`; the engine differs after opening; in-memory SQLite; DuckDB and other single-owner engines; secure SQLite on Windows, whose custody verifier cannot cross a thread boundary) the thread is not started and the lease is renewed on the runner's own connection from the main loop, with one log naming the reason: `warn` where a thread used to run (file-backed SQLite with no same-engine connection, secure SQLite on Windows), `debug` for engines that never had a second connection (in-memory SQLite, DuckDB, JSON). A thread that fails to start logs its actual error. That fallback is safe but gives up the protection against a long synchronous handler: renewal can be delayed by it, so keep `leaseTtlMs` well above the longest synchronous section. A thread-spawn failure, a start-handshake timeout, or the thread dying mid-run fall back the same way. The worker entry is a separate build entry resolved via `import.meta.resolve('@happyvertical/smrt-jobs/worker-liveness-thread')`.

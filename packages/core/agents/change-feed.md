# smrt-core/change feed

Module semantics for `src/change-feed.ts`. Package orientation, the cross-module
invariants, and the traps that apply before editing anything live in
[../AGENTS.md](../AGENTS.md) — read that first.

## Change Feed (#1758)

Adapter-agnostic change-observation spine (`src/change-feed.ts`) — the server half of the client/mobile sync contract (PRD #1755):

- `_smrt_changes` system table: one append per framework save/delete via a GlobalInterceptors writer registered at framework init. Deletes are tombstones (`operation: 'delete'`). `_smrt_*` tables are skipped. Feed-append failures never fail the user's write; they log at most once a minute per database and table (with a suppressed count; a framework transaction's failures count against its root database, and a private in-memory database's buckets are held weakly by its handle). The dropped change is not marked in the feed — sequences stay contiguous and `resyncRequired` only covers pruned or foreign cursors — so a consumer is not told it missed it (recording such gaps is a separate, tracked change; since #5438 a *staged* entry the PostgreSQL drain cannot sequence is kept as a gap marker instead, see below). On PostgreSQL the append-failure warning limit is kept per root handle, so separate pools on one database can each log the same table's failure within one minute. On PostgreSQL, `_smrt_append_change` catches the INSERT in an exception subtransaction and returns SQLSTATE as data, so swallowing/retrying a best-effort failure cannot leave a caller-managed transaction aborted with `25P02` (#2026); the feed row still commits or rolls back with the caller transaction. Raw-handle/read initialization checks for both the table and helper before issuing any DDL; a cold schema/helper install acquires the same transaction-scoped `('smrt', 'system-tables')` advisory lock as bootstrap before its first DDL and rechecks inside one server-side statement, while schema migration/bootstrap remains the authoritative replace path. No dirty-check: a field-unchanged `.save()` appends a spurious `update` entry (diff-aware paths like `getOrUpsert`/sync-apply short-circuit before `save()` and append nothing; they compare JSON values structurally and key-order-insensitively via `src/utils/json-equal.ts`, #4604); subscribers must tolerate spurious entries — they are convergent.
- Sequences: allocated as `MAX(seq)+1` inside the INSERT with conflict retry (a jittered pause of at most 40 ms between attempts, so two tight-loop writers cannot starve one another — #3062; retries run on a 2 s monotonic budget with a 20-attempt floor, checked only between attempts, and an exhausted budget throws an error whose message says so and repeats the last database diagnostic, keeping its `code` and `cause` — #5271) — committed rows stay contiguous, so commit order == seq order on SQLite/Postgres/DuckDB (deliberately NOT identity/serial: those allocate before commit and break the cursor guarantee under concurrent writers).
- Staged appends (PostgreSQL, #2649): `MAX+1` costs a *wait* — the loser of a primary-key race waits for the winner's whole transaction — so an append inside a caller transaction that already wrote rows would let a long write transaction and an ordinary concurrent request form a real lock cycle (`40P01`, found downstream in willgriffin/willgriffin.dev#457). `_smrt_append_change` therefore checks `pg_current_xact_id_if_assigned()` (PostgreSQL 13+): when the caller already has a transaction id it stages the entry in `_smrt_changes_pending` (identity key, conflicts with nothing, never waits, still rolled back with the caller) and `appendChange()` returns **`null`** instead of a sequence. `_smrt_drain_changes()` moves *committed* staged rows into `_smrt_changes` with contiguous `MAX(seq)+row_number()` sequences under a **try-only** advisory lock (and, since #5271, a try-only head lock), so the drain does not wait either (unless asked to: see the waiting drain, #5403). Draining is driven from JavaScript, never inside the append helper: an entry sequenced invisibly server-side would get no live `_events` signal while the append's own signal carried a higher sequence, and a subscriber resuming from that `Last-Event-ID` would skip it permanently. `drainChangeFeed(db)` is called best-effort by `getChangesSince()`, by `pruneChangeFeed()`, and by the append path itself (throttled to one drain per 250 ms per database, bypassed immediately after this process staged an append). The append path issues ONE drain statement (a single bounded pass) and nothing else — the caller may own the surrounding transaction, and a second statement there could fail and abort it behind the feed's own error-swallowing (#2026); the helper's whole body, preflight included, sits inside its exception boundary for the same reason. It still settles that drain's signals in order without spending a statement: a drain that allocated anything assigns a transaction id, so an append that then takes the DIRECT path proves the drain committed, and its signals publish ahead of the append's own; a deferred append proves nothing and queues them. Signals for drained entries publish only after a follow-up probe proves the drain committed, so an uncommitted drain can never advertise a sequence a rollback releases for reuse. `getChangesSince()` additionally holds back everything the handle's own drains allocated while a transaction id is still assigned at read time (a per-handle watermark, so later reads in the same transaction keep holding back), and `bootstrapSystemTables()` refreshes the helpers before its schema-version fast return so an already-stamped database does not keep the deadlocking function. Consequences: the cursor guarantee is unchanged (one `MAX+1` writer at a time, only over committed work), but a staged entry becomes visible one drain after its transaction commits, its log position is drain order rather than statement order, and it publishes its live `_events` signal at drain time (post-commit — the old pre-commit signal could describe a rolled-back write). SQLite/DuckDB keep the direct insert unchanged. Residual: an append issued as a transaction's *first* statement still allocates inline — it holds no row locks then, so it cannot close a cycle, but it can make other direct appenders wait for that commit; issue explicit `bumpChangeFeed()` calls after the write or outside the transaction. A deployment that writes only through transactions and reads the feed from a connection that cannot write must schedule `drainChangeFeed()` on a writable one.
- Head lock (PostgreSQL, #5271): every `_smrt_changes.seq` allocator takes the transaction-scoped advisory lock `(hashtext('smrt-change-feed-head'), hashtext(<oid of _smrt_changes>::text))` before reading `MAX(seq)` — one lock per feed table, so separate schemas never share it — after first taking `LOCK TABLE _smrt_changes IN ROW EXCLUSIVE MODE` (so the head lock is never held while waiting for the relation lock a `SHARE` holder blocks), both inside the helper's exception boundary. Direct READ COMMITTED single and batch appends WAIT for it; the drain only TRIES it, and only when a non-sensitive staged row exists, and takes the relation lock `NOWAIT` (a refusal is a skipped pass), so a reader whose role holds a table-level INSERT/UPDATE/DELETE/TRUNCATE privilege never waits on the head or behind a `SHARE` holder (the read serves the committed horizon and a later drain sequences the staged rows) and a purge of sensitive rows never holds it. `LOCK TABLE` needs a table-level INSERT/UPDATE/DELETE/TRUNCATE privilege while the INSERT itself accepts column-level grants, so a role granted INSERT on `_smrt_changes` only per column skips the explicit lock (`has_table_privilege`) instead of failing every append with `42501`; for that role an append's relation lock comes after the head lock, so a `SHARE` holder that also appends can form a cycle with a waiting appender (`40P01`; the victim's entry is staged since #5438); grant table-level INSERT to close the exception. The drain no longer has it (#5403): for such a role it takes the same relation lock before the head with a zero-row insert under a 1 ms `lock_timeout`, and a refusal ends the pass (`relation_busy`) holding nothing. The helpers must stay `VOLATILE`: each statement's fresh snapshot after the lock, plus PostgreSQL making a commit visible before releasing its locks, is why a holder never collides. Guarantee: cooperating READ COMMITTED allocators are serialized and never repeat a primary-key race; a single wait is bounded only by `lock_timeout`/`statement_timeout` (a lock timeout or deadlock stages the entry since #5438; a cancel is returned as data). The staging decision does not depend on `_smrt_changes_pending` existing: if that table is missing, a written or fixed-snapshot append fails with its `42P01` returned as data (the entry is warned and dropped; bootstrap recreates the table) instead of allocating from a stale snapshot or waiting on the head while holding a transaction id. Residual: a transaction whose first statement is a direct append holds the head until it ends (as it held the unique-index entry before); an application advisory lock or `LOCK TABLE` taken in the opposite order can still form a cycle, which PostgreSQL breaks with `40P01`; a direct append that loses is staged (#5438). **Fixed-snapshot isolation:** under REPEATABLE READ or SERIALIZABLE (checked with `current_setting('transaction_isolation')`; READ UNCOMMITTED counts as READ COMMITTED) the append helpers stage instead of allocating, written or not, and `appendChange()` returns `null`; the drain allocates nothing there. With `default_transaction_isolation` set to `repeatable read` or `serializable`, every append stages and every drain on those connections returns without allocating, so the feed makes no visible progress — cursor readers and SSE subscribers see nothing new and `_smrt_changes_pending` grows, with nothing logged — until `drainChangeFeed()` (or a feed read) runs on a connection whose transactions are READ COMMITTED (e.g. connected with `options=-c default_transaction_isolation=read\ committed`); nothing is lost, and the pending row count is the signal to watch. `40001` is not retried as contention. **Rollout:** v6 bodies (all four identities, the compat drain included) carry the v6, v5 and v4 markers, so v5/v4 processes keep them. Older code can still put v5 bodies back — an older CLI's `db:migrate-uuid` replaces unconditionally, and an older cold initializer can reinstall both drain overloads — so upgrade the CLI before running `db:migrate-uuid`; the next v6 process start reinstalls v6. While older bodies are installed the pre-v6 guarantee applies, not v6's: the primary key still rejects a duplicate sequence, but an older writer can exhaust its attempts and drop an entry (warned, not marked), and a REPEATABLE READ / SERIALIZABLE allocator running an older body can insert from a stale snapshot below a cursor a consumer already observed once retention freed that slot, which the key cannot catch (pre-existing). Reinstalling v6 stops new occurrences but recovers neither; consumers that may have missed entries in that window need a full refresh. Zero-conflict operation holds only once older in-flight allocations have finished and every body is at least v6 (v7 bodies carry the v6 marker); check with `SELECT p.oid::regprocedure, p.prosrc LIKE '%smrt-change-feed-helpers:v6%' AS floor, p.prosrc LIKE '%smrt-change-feed-helpers:v7%' AS current FROM pg_proc p WHERE p.proname IN ('_smrt_append_change','_smrt_append_changes','_smrt_drain_changes')` (five rows since #5402).
- Drain status and lock release (PostgreSQL, #5402): the drain body lives in `_smrt_drain_changes(integer, text[], jsonb)` (the **status drain**, marker v7 — v8 since #5438 — which also carries v6, v5 and v4); `_smrt_drain_changes(integer, text[])` and `_smrt_drain_changes(integer)` delegate to it with no options, each inside its own exception boundary, and return only its entry and error rows, so their columns are unchanged and a role that may execute a delegator but not the status drain gets `42501` as an error row, never an aborted transaction. The status drain ends its result with one status row (`drained_seq` and `error_code` NULL) carrying `status` (`drained`, `empty`, `in_transaction`, `fixed_snapshot`, `drain_busy`, `relation_busy`, `head_busy`), `backlog_remaining` (a committed non-sensitive staged row is still visible; NULL when unknown) and `helpers_current` (the other four identities carry v7; NULL on an `empty` pass). Every statement that can take a lock — the staging probe, the drain lock, the feed table's insert lock, the head lock, the sensitive purge — runs in one block; a pass that finds no work raises a private SQLSTATE that block catches, and the rollback releases everything it took. So a skipped pass issued as the first statement of a caller transaction no longer blocks other drains until that transaction ends; only a pass that sequenced or purged something keeps its locks (and, as before, its uncommitted sequences) until the caller's transaction ends. The sequencing statement is the last statement of that block and the status extras are computed in a separate block afterwards, because rows a `RETURN QUERY` appended stay in the result even when a later error rolls the block back: **a call that returns an error row must have all its entry rows discarded** (the JavaScript parsers throw on any error row before reading entries). The install creates the status drain first and makes its owner and EXECUTE grantees equal to the two-argument drain's (grantee sets compared normalised, `acldefault` standing in for a NULL ACL); if that cannot be done the whole install rolls back. **Helper probe states** (`change-feed.ts`; as of #5438): `current` (all six identities, the version routine included, v8), `mixed` (status drain at least v7, so it is called directly, but the set is not current — an older installer restored its bodies, or a v8 install was refused), `usable-older` (every existing identity carries v6, the status drain missing or older than v7), `outdated` (some identity missing or older than v6), `missing` (no feed table). `missing` and `outdated` install as before, and a refused install of `outdated` bodies throws an error saying the database owner must install the current helpers (pre-v6 bodies do not keep the cursor guarantee). `usable-older` and `mixed` keep working on what is installed: they are upgraded only on an autocommit root handle (one with `transaction()`, `beginTransaction()` and `close()`, no `commit`/`rollback`, not a known transaction, and whose client does not report an open transaction block), never on a handle that may be inside a caller's transaction, and a refused upgrade warns once per handle and probe result. Upgrade note: permission-managed deployments get the new routine from the current CLI's permission plan (an older planner reports it as an unknown routine); a runtime role that may not replace v6 helpers keeps running on them with one warning instead of failing initialization, while pre-v6 helpers it may not replace now fail with an owner-upgrade message instead of a bare `42501`.
- Waiting drain and root drainer (PostgreSQL, #5403): a try-only drain fails while the head is held *or queued for*, so under steady direct appends from several connections staged entries could stay invisible for as long as the load lasted. The status drain takes options `waitMs` (wait mode) and `firstStatement`. **Wait mode** waits for the drain lock, then `ROW EXCLUSIVE` on `_smrt_changes_pending`, then the head — holding only the drain lock and that staging lock while it waits, neither of which a head holder requests — then takes the feed table's insert lock `NOWAIT` (refusal: `relation_busy`, everything released). All waits share one deadline: the budget is capped below the session `statement_timeout` (`statement_timeout − elapsed − max(10 %, 50 ms)`), recomputed before every blocking step (the staging probe included, so an `ACCESS EXCLUSIVE` holder on the staging table cannot stall the pass), applied as a local `lock_timeout` never below 1 ms (PostgreSQL reads 0 as no limit), and a spent budget ends the pass as `timeout` before it waits; a lock wait that runs out is also `timeout` (the block's rollback releases everything and reverts `lock_timeout`), never an error, except once the sequencing statement has started. `lock_timeout` is restored to the caller's value before sequencing. A role with only column-level INSERT takes the feed table's insert lock before the head (zero-row insert, 1 ms limit) in both modes, so no drain ever waits for a relation lock while holding the head; holding that lock while it waits for the head can form a cycle only with a transaction that holds the head and then requests `SHARE` or stronger on `_smrt_changes` (the opposite-order residual above). **`firstStatement`** makes the drain return `in_transaction` unless it is the first statement of its transaction (`statement_timestamp() = transaction_timestamp()`; the call must use the simple query protocol, since the extended protocol stamps a new statement time after Parse began the transaction; resolution is the server clock's — PGlite's is milliseconds). **Which handle calls what:** only a *verified root* (a PostgreSQL handle with `transaction()`, `beginTransaction()` and `close()`, no `commit`/`rollback`, not a known transaction) whose client does not report an open transaction block (PGlite's `isInTransaction()`), and whose probe found the status drain current, calls the status drain directly — its statements are autocommit, so a refusal aborts nothing and makes it fall back to the two-argument drain; every other handle, possibly inside a caller's transaction, calls only the protected two-argument drain, and the write path stays one statement. `drainChangeFeed(db, { wait: true })` runs one wait-mode drain (2 s) on such a root (probing its helpers first when the handle was never probed) and is otherwise unchanged. **Root drainer:** each verified root gets one detached drainer (`runOutsideWriteContext`, single-flight, one trailing pass for a kick during a pass), whose passes are wait-mode, `firstStatement`, simple-protocol calls (budget 2 s, doubling after each `timeout` to 30 s, reset on progress, halved after a `57014` error row). It is kicked by the root's first feed call in the process (a drain, an append or `getTableVersion`), a framework transaction on the root committing staged work, an append on the root that staged, a caller's drain on the root whose status reports `*_busy`, `timeout`, `fixed_snapshot`, `backlog_remaining` or older helpers, and the trailing pass armed when the 250 ms throttle skips a write-path drain on the root (skipped if a drain on the root ran after the skip). A kick runs after a 250 ms coalescing window. It re-arms (backoff 250 ms doubling to 30 s, reset on progress) while the last status reports backlog, busy, timeout or `in_transaction`, or backlog is unknown and the last batch was full, and after an error row; it stops when a status reports none. A thrown pass (connection failure) re-arms at the same backoff without limit while the root has observed outstanding work (a status reported it), and stops after five consecutive failures otherwise; positive closure (PGlite `closed`, a pool `ending`/`ended`) or a closed-pool error ends it silently on first sight; a collected root ends it; every timer is `unref()`'d. It never runs while the root's client reports a transaction block (and the server-side `firstStatement` guard covers the window between that check and the statement). Its signals keep the `drainCommitted` proof. On `fixed_snapshot` (root default isolation REPEATABLE READ/SERIALIZABLE) it drains once in `root.transaction()` whose first statement is `SET TRANSACTION ISOLATION LEVEL READ COMMITTED`, publishing after commit; not on a root whose client reports transaction state (PGlite), which is warned once. On `helpers_current = false` it probes and reinstalls the helpers, at most once per root per probe result, never from a caller's path. Warnings (through the existing per-database limits): backlog this drainer has observed for 30 s, a failed pass (not a closure), a refused helper upgrade, an undrainable fixed-snapshot root. D5 as implemented: while a process holds a root, backlog any status on it reported is retried until a status reports none, at most ~60 s apart (a 30 s wait plus a 30 s re-arm). **Not covered:** backlog committed by a caller-owned or raw transaction or another process after the drainer stopped at an empty backlog, with no later feed call on any root — schedule `drainChangeFeed(root, { wait: true })` on a writable connection for such deployments. Upgrade notes: a process issues background drain statements on its roots while a backlog remains; a waiting pass holds one pooled connection for up to its budget (≤ 30 s, below `statement_timeout`), so a one-connection pool's foreground queries can queue behind it — size pools accordingly; K pools on one database run K drainers queued on the drain lock, each holding a connection while it waits.
- Stage instead of drop (PostgreSQL, #5438): a direct append (single or batch) whose allocation fails with `55P03` (lock timeout), `40P01` (deadlock victim) or a `23505` whose `CONSTRAINT_NAME` is the feed table's primary key is staged in the same statement instead of returned as an error: the helper first converts every tenant id to the **feed** table's live column type (the failure may have come before the direct insert's own conversion, and a value only the staging column accepts would fail every drain batch behind it), takes `ROW EXCLUSIVE` on `_smrt_changes_pending` `NOWAIT` (a role without a table-level privilege for it: a 1 ms local `lock_timeout`, restored), then runs the staged insert; any failure there returns the original error and stages nothing. The single helper returns the staged marker (`allocated_seq` NULL, `error_code` NULL) with `staged after <SQLSTATE>: <message>` in `error_message`; the batch helper returns one row per `entry_index` in the same shape (its direct insert now runs as its own statement and rows are returned only after it succeeded, so a call never mixes allocated and staged rows). `57014` (statement timeout or cancel) stays an error and stages nothing; so does every other SQLSTATE (data, privilege, a duplicate on another constraint). JavaScript needs no new path: `null` means staged and kicks the root drainer. **Upgrade note (breaking):** `appendChange` resolves `null`, and `appendChanges` resolves `null` for each entry, where they threw `55P03`, `40P01` or a sequence-key `23505`; `bumpChangeFeed` resolves where it threw. Callers that caught those errors to run a failure path, or that treated a thrown append as "not recorded", now get a staged entry the next drain delivers; a sequence-key `23505` from an older body no longer reaches the #5271 retry loop. v6 processes on v7 bodies read the staged marker as an ordinary staged append. **Finding and repairing an undrainable staged entry** (since #5438 the drain isolates such a row into a gap marker itself; this applies to a database still on v7 helpers, or when the marker cannot be written): the drain sequences committed staged rows in batches of 1000 in `pending_id` order, and one row the feed table rejects fails the whole batch, so a repeated drain failure (the "failed to sequence entries staged inside caller transactions" warning, or a status-drain error row with the same SQLSTATE every pass) with `_smrt_changes_pending` not shrinking points at one. Find it with `SELECT * FROM _smrt_changes_pending ORDER BY pending_id LIMIT 1000` and test each row against the feed's types (for a tenant id: `SELECT pending_id FROM _smrt_changes_pending WHERE tenant_id IS NOT NULL AND tenant_id::text !~* '^[0-9a-f]{8}-([0-9a-f]{4}-){3}[0-9a-f]{12}$'` when the feed column is uuid); then correct it (`UPDATE _smrt_changes_pending SET tenant_id = NULL WHERE pending_id = …`, which makes the entry global) or delete it, and tell consumers of that table to resync if it was deleted. The fallback's pre-staging conversion keeps it from creating such rows.
- Gap markers (PostgreSQL and PGlite, #5438, first release: storage, isolation and dormant conversion; marker v8). `_smrt_change_gaps` (joins the system schema under a new version; `gap_id` native uuid on PostgreSQL and DuckDB, TEXT on SQLite; `tenant_key` text everywhere; indexes on `table_name` and `converted_seq`; also created by the helper install DDL) holds one row per lost entry: table, private evidence (`row_id`, possibly NULL, and `operation`), tenant key, `created_at`, `blocked_at`, `converted_seq`, `reconciled_at`. **Staged phase:** the batch now runs in its own block and hands rows back only after every block committed; it compares staged rows removed with feed rows inserted, and on a mismatch (a trigger that silently drops an insert) or a row-attributable error (SQLSTATE class 22, class 23 except a `23505` on the feed's primary key, or `P0001`) rolls the batch back and moves up to 64 rows one at a time, each with the same receipt check and classification. A refused row is replaced by a marker, and its staged row is deleted only after the marker's insert returned its row; any other failure (lock timeout, privilege, resource) leaves the row staged and ends isolation for the pass, so a retryable failure never becomes a marker. A non-attributable batch error is still the call's error row (and the #5271 retry for a sequence-key `23505`). **Marker phase:** its own blocks, independent of the staging table and the staged phase (a missing staging table or a failed staged phase still lets markers convert); it runs only while the `_smrt_backfills` row `@happyvertical/smrt-core:change-feed-gap-delivery:v1` exists, read under the drain lock and locked `FOR SHARE` (`NOWAIT` in try mode), and **nothing in this release creates that row, so delivery is off everywhere**. When on, up to 200 markers per pass (oldest first; blocked ones only with `retryBlocked`, which a root's drainer sends every ten minutes) each get a feed row with `row_id` NULL and the stored operation `gap`; the insert must return exactly one row, then the marker records `converted_seq` and the feed row's canonical tenant text and stays as evidence. A failed conversion sets `blocked_at`; later markers proceed. Markers and evidence of tables in the live sensitive set are deleted (drain and retention, #2937); nothing else deletes an unconverted or reconciled marker. Gap rows are never returned as drain entries, counted as drained or signalled: the call returns one **allocation row** (`drained_seq` NULL, `drained_operation` `allocated`, first and last sequence as text in `drained_row_id` / `drained_tenant_id`) that every parser keying on `drained_seq` ignores and this build adds to the uncommitted-drain mark; `getChangesSince` never places a gap row in `changes` (reader handling of gaps comes with delivery). The status row's `error_message` carries counts-only notes (`isolated=N`, `gaps converted=N`, `gaps blocked=N`, `gaps: <SQLSTATE>`), logged at most once a minute per database; `backlog_remaining` also covers unconverted, unblocked markers while delivery is on. **Versions:** `getTableVersion()` on PostgreSQL reads `_smrt_change_feed_version(text)` (a new routine identity, owner and EXECUTE grantees made equal to the two-argument drain's at install, like the status drain) after a non-raising probe (`to_regprocedure`, `has_function_privilege`) cached per handle; the routine returns the table's `MAX(seq)`, the horizon, the staged count and the count of markers not converted (unconverted, blocked and reconciled), all in one statement, inside an exception boundary that catches `query_canceled`, so it never raises. Unknown (a missing table, a role that may not read the gap table) or routine absent while the gap table exists → an unrepeatable value (full `200`). Conversion adds a sequence and removes a marker in one transaction, so versions never decrease; reconciled markers count for good. **Retention:** `pruneChangeFeed` deletes the feed prefix first, then evidence with `converted_seq` below the retained floor (`prunedGapRecords` in its result on PostgreSQL; `dryRun` counts both, deletes neither); an exit between the two leaves orphan evidence for the next sweep. SQLite and DuckDB issue no statement on the gap table yet. CLI: `smrt db:feed-gaps status` (SELECT only) reports unconverted, blocked, reconciled, positioned and positioned-without-evidence counts; `smrt db:migrate-uuid` holds the system tenant columns back while an unconverted, unreconciled marker has a non-UUID `tenant_key`. **Upgrade notes:** a new system table, indexes and grants (permission-managed deployments get the table and routine from the current CLI's plan); helpers move to marker v8 (v7 processes keep calling the status drain, whose columns are unchanged); a staged entry the feed refuses no longer stops every later drain or disappears — it becomes a marker that counts in its table's version (`smrt db:feed-gaps status` lists them); during a rolling upgrade a v7 process does not count markers in versions. Hardened databases: the gate's `FOR SHARE` needs UPDATE on `_smrt_backfills`, which the planner does not grant the runtime role; it is only attempted once delivery is enabled.
- Entry tenant: the writer records each change under the row's **real owner**, resolved by the registry (`src/change-feed-tenant.ts`, a leaf module the registry fills via `setChangeFeedTenantFieldResolver` exactly like the sensitive-class resolver). Every applicable ownership field is compared — runtime ownership registrations (the tenancy package's `{ field }`), the declared/ownership tenant column (`ObjectRegistry.getOwnershipTenantColumn`), `@tenantId`-marked fields and `tenant_id` — so a runtime source cannot hide a declared owner that disagrees with it. The `tenantId` property is only the fallback for a class the registry does not know. An entry recorded as global (`NULL`) is served to every tenant, so a custom field (`organizationId`) must never fall through to it. A row whose owner cannot be resolved — its ownership fields name different tenants, or the registry lookup throws — is not recorded, rather than being recorded under any one tenant or as global; it logs its own warning at most once a minute per database and table (with a suppressed count, through the same limiter as append failures but in separate buckets, so neither silences the other). Attribution comes from what the write persisted or removed, never from fields that can drift from it, and is carried per write in a `WeakMap` keyed by the interceptor context object (`noteChangeFeedWriteOwner`/`changeFeedWriteOwner`), so an interceptor that replaces `context.metadata` cannot drop it. A **save** (single or bulk) is recorded under the ownership values in the serialized row it writes (after `transformJSON()` and the framework's column rules); a save whose saved data omits a stored ownership column (a `transformJSON()` that drops it, or a field left unset) leaves that column to the database — an update or an upsert onto an existing row keeps the stored value, an insert takes the column default — which the instance field need not match, so ANY such save (insert, upsert or update) is **not recorded** (the "could not be resolved" warning, rate-limited as above) rather than recorded under the mutable instance value. This applies to every stored ownership column, declared or runtime-registered: `prepareSave()` writes NULL for an unset declared tenant column only when the conflict target includes that column, so a declared column that a `transformJSON()` drops on a model whose conflict target excludes it (for example `conflictColumns: ['id']`) is omitted too. A natural-key save that adopts a stored same-owner row is recorded under the adopted row's id (`rebindChangeFeedWriteRowId`), not the id `prepareSave` generated. A **delete** (single or grouped) is recorded under the owner the **removed row** had: `deleteSyncRows()` returns the class's stored ownership columns (`CAST(… AS VARCHAR)`, so native DuckDB UUIDs arrive as canonical strings) from the DELETE statement itself, so no separate owner read can observe another row version, race a concurrent owner change, or abort a caller-managed PostgreSQL transaction; the JSON adapter (no RETURNING) reads the rows inside the embedded write queue just before its delete. Neither an ownership field cleared or changed in memory nor a model `afterDelete` hook that clears it can turn the tombstone into a global or another tenant's entry. Returned rows are matched to the bound ids in the engine's canonical id form (`normalizeSyncRowId`: native UUID ids canonicalized, text ids exact — never case-folded). Only when the statement removed no row under the id **and** a one-column existence check (`existingRowIds`, `id` only — no privilege the delete's `RETURNING` does not already need) finds no stored row does the provisional owner apply — the in-memory owner the writer's `beforeDelete` read before any model hook ran; a row still stored (a trigger suppressed the delete) records nothing. Each write captures the id its statement bound together with the owner (`ChangeFeedWriteOwner.rowId`), so a hook that reassigns `id` afterwards cannot pair the owner with another row's id. Each write also takes ONE ownership snapshot (`changeFeedOwnerPlan`) before its statement and resolves the returned row against it, so a registration that changes while the statement is pending cannot read an unreturned column; a stored ownership column the returned or read row does not carry (not returned, or missing from the physical table / JSON row) is unresolved, never empty. A **revision claim** (`claimRevision()`) is recorded under the stored owner: the embedded path reads it from the row it already compares, other SQL adapters return it from the guarded `UPDATE … RETURNING` itself. Stored ownership columns are resolved against the merged (inherited) field set persistence serializes, so a subtype whose manifest lists only its own fields still reads the owner column it inherits; write paths resolve that set (`ObjectRegistry.getAllFields`) once before the snapshot, and a subtype whose merged set is still unresolved is an unresolved owner (nothing recorded), never "no owner column". A non-string owner value (an uncast DuckDB UUID wrapper) is unresolved, never skipped into a global entry. Upgrade note: the DELETE and claim statements now return the stored ownership columns (`DELETE … RETURNING`, `UPDATE … RETURNING`), so the database role needs `SELECT` on them; a role without `SELECT` on a runtime-registered ownership column now gets a permission error (`42501`) on delete instead of a delete with no feed entry. Such a role cannot load the model anyway (a load reads every column, and the delete already returned the declared tenant column), so it is not a supported setup, and a loud failure is preferred to a missing feed entry. A stored ownership column missing from the table likewise fails the statement, as a save of that class already does. Upgrade note (breaking): a save (insert, upsert or update) whose saved data omits a stored ownership column — runtime-registered or declared (`tenantScoped`) — no longer produces a feed entry; models whose `transformJSON()` drops the owner column, or that leave it unset for the database default to fill, are affected (a declared tenant column inside the conflict target is always written, as NULL when the serialized row lacks it; outside the conflict target, such as `conflictColumns: ['id']`, a serializer that drops it is affected like a runtime-registered column) — keep the owner column in the saved data, or resync consumers of that table. Known limits: entries an older build already recorded with `tenant_id = NULL` for such models (including PostgreSQL entries staged before the upgrade and drained after it) stay global; correcting retained history needs a resync boundary or a backfill, which changes persisted data or the cursor contract and is tracked separately.
- Tenant typing (#3297): on PostgreSQL `_smrt_changes.tenant_id`, `_smrt_changes_pending.tenant_id` and the dispatch tables' `tenant_id` are native `uuid` on fresh installs (TEXT elsewhere, and on existing installs until `smrt db:migrate-uuid` converts them in a maintenance window). The helpers (marker `smrt-change-feed-helpers:v5`, now v6 — see Head lock) coerce each tenant id to the LIVE column type through `jsonb_populate_record(NULL::<table>, …)`, so one body serves TEXT, uuid and the mixed state mid-conversion, and `_smrt_drain_changes()` returns `drained_tenant_id` as text. v5 bodies also carry the v4 marker so an older process's probe keeps them during a rolling upgrade; `db:migrate-uuid` installs them in its own transaction before converting. Upgrade every writer before converting: an older process that reinstalls its v4 drain cannot return a uuid tenant id. Tenant ids written here must be UUIDs (or NULL); `_smrt_ai_usage.tenant_id` and `_smrt_run_once_claims.tenant_id` stay TEXT (caller-supplied scope strings).
- `getChangesSince(db, { since, tables?, tenantId?, limit? }) → { changes, cursor, resyncRequired?, resyncCursor? }`: strictly monotonic cursor; polling with returned cursors misses no committed change and never repeats one. A cursor that cannot be served incrementally — pruned below the retained `[floor..horizon]` run, or foreign/ahead of the horizon — gets `resyncRequired: true` with empty `changes`, an unadvanced `cursor`, and `resyncCursor` set to the current horizon so clients can full-refetch then resume incrementally; detection runs on the UNFILTERED log so `tables`/`tenantId` filters never trigger or mask it. On embedded engines the read goes through the per-database write queue, which every framework write transaction holds for its whole duration, so a read from outside a transaction waits for it and never serves its uncommitted feed rows (the root shares the transaction's connection on SQLite and DuckDB, so it would otherwise see them); a read inside the transaction is re-entrant and sees its own work. The retained floor is re-read after the page query, so a retention prune that commits between the bounds read and the page read is answered with `resyncRequired` rather than a cursor advanced past the deleted rows. `getTenantScopedChangesSince()` resolves tenant via the DispatchBus resolver hook (fail-closed: tenancy on + no context → global rows only; tenant `T` sees `T` + global rows, never another tenant).
- `getTableVersion(db, table) → number`: the per-table change version (`MAX(seq)` for the table **plus that table's staged-but-undrained count**, so a staged write still moves the ETag and cannot false-304 a client; the sum is monotonic because draining `n` staged rows raises the table's `MAX(seq)` by at least `n`, and both terms are read in ONE statement — separate reads let a drain be counted twice, minting a version a later write re-mints; replica-stable, with no per-process divergence), the ETag source for zero-query conditional GETs (#1765). Advances on any framework write to the table (CRUD and sync-apply, which all `save()`/`delete()`). A table with no retained entry of its own falls back to the global horizon (never a resettable low value) so an all-pruned table cannot false-304 a stale client; only 0 when the feed is empty. On PostgreSQL it also counts the table's gap markers that are not converted and is read through a routine that cannot raise (#5438, see Gap markers).
- Generated `_changes` routes: REST (`GET {basePath}/_changes`, requires `authMiddleware`, otherwise 401 — per-model `api.public` does NOT apply) and SvelteKit (`{routesDir}/_changes/+server.ts`, requires an authenticated principal on `locals`; opt out via `sveltekit.changesRoute.enabled: false`). Query params: `since`, `tables` (comma-separated), `limit`. Responses stay HTTP 200 in the resync state — `resyncRequired` is protocol state, not an error, and `resyncCursor` is the resume cursor after the client completes a full refetch.
- Retention: `pruneChangeFeed(db, { maxAgeMs?, maxRows?, dryRun? })` — scheduled since #2375 by `runRetentionSweep()` (30-day default), so nothing needs to call it directly; `dryRun` counts the same predicate instead of deleting. Pruning deletes oldest-first and always retains the newest entry (a non-empty feed is never emptied), which is what makes pruned-cursor detection provable. The age bound is a **prefix** bound — everything below the oldest entry still inside the window — because `created_at` and `seq` are not co-monotonic (writer clocks skew, and a staged entry carries its stage-time stamp into a later-assigned sequence); deleting by timestamp alone could punch a hole in the middle of the retained run, where `since < floor - 1` cannot see it and keeps caught-up consumers polling normally. Raw-SQL writes are invisible to the feed (same documented gap as the #1499 cache); `bumpChangeFeed(db, { table, rowId? })` is the manual escape hatch.


## Durable row sync metadata (#4673)

Configure the current local writer with `setDatabaseSyncDeviceId(db, uuid)`.
An ordinary row stays untracked until a trusted caller opts in with
`object.save({ trackSync: true })` or applies an incoming revision. Subsequent
local saves and timestamp claims advance the counter and stamp the configured
device. Tracked creates require a supplied ID and strict insert. Load an
existing tracked row by ID to update it.

A trusted replay supplies `save({ sync: { originDeviceId, revision } })` with
a positive safe-integer revision. A replay advances the row only when its
revision is higher, or when the revision is equal and its device ID sorts
after the stored ID. Core still uses the local `updated_at` compare-and-swap
predicate. The caller supplies the authenticated actor and tenant context.
This API is separate from the generated `sync/apply` protocol.

`delete()` physically removes a tracked row and records its next sync revision
in `_smrt_sync_tombstones` in the same transaction. Tracked cascade deletes do
the same. A tracked SET NULL reference stays live and advances its writer,
revision and timestamp. A trusted incoming `delete({ sync: { originDeviceId,
revision } })` can record a deletion for an ID that has never been present
locally. The ledger stores the physical table, row ID, qualified model and
tenant, and remains available after change-feed retention. Its entries
represent tombstones. Ordinary model reads only see live rows. A new identity
can reuse a deleted natural key, and a replay using the deleted ID conflicts.

Remote LibSQL coverage currently depends on an SDK fix for its transaction
and parameter-binding support. A rollback probe against sqld with
`@happyvertical/sql@0.111.3` persisted changes even when the callback threw.
The in-process LibSQL test branch exercises Core’s remote-path selection and
write predicates. Set `SMRT_TEST_LIBSQL_URL` to exercise the real adapter on
a disposable sqld database.

## Credential-bearing tables are never disclosed (#2937)

`src/change-feed-sensitivity.ts` is a leaf module (it imports nothing, so
`change-feed.ts`, `change-signals.ts` and the registry can all consult it
without a cycle) holding the tables whose **row id or payload is a secret**. A
table joins it two ways: by name, via the baseline
`CHANGE_FEED_CREDENTIAL_TABLES` (`sessions`, `users_cli_auth_requests`,
`users_magic_link_tokens`, `magic_link_tokens`, `api_keys`,
`nostr_identities`), or because a class declared `@smrt({ sensitive: true })`
and registration pushed its resolved table name across
(`declareChangeFeedSensitiveTable`, called from both the decorator and the
manifest-stub registration paths). Both are needed: the declaration is the
package's own contract but only binds in a process where that package
registered, while the name baseline is all the read path has when serving a
database another process writes. The set is **monotonic** — `sensitive: false`
is not an opt-out and nothing removes a name — so a consumer whose domain
table is named `sessions` loses feed coverage for it and must rename it via
`@smrt({ tableName })`.

`isChangeFeedObservableTable()` ANDs the sensitivity check with
`CHANGE_FEED_EXCLUDED_TABLES`, and the refusal is enforced at four points, not
one: the interceptor write path; `appendChange`/`appendChanges`, the lowest
write API, so `bumpChangeFeed()` and any other escape hatch are covered (a
refused append returns `null`, indistinguishable from a staged one);
`deliverLocally` in `change-signals.ts`, which also catches a signal broadcast
by a peer replica running an older build; and **`getChangesSince()`**. The
read-side refusal is what makes upgrading sufficient — rows an earlier version
already wrote stay in the log but are never served. A caller-named sensitive
table is dropped from the `tables` filter rather than erroring, so nothing
confirms the table exists, and a request naming *only* sensitive tables gets
an empty page rather than an unfiltered one. Filtered rows never hold the
cursor back: an exhaustive page still advances to the served horizon.

The PostgreSQL drain also refuses them (#2982). Every drain passes the live
sensitive set to `_smrt_drain_changes(limit, excluded_tables)`. Under the drain
lock it deletes staged rows for those tables before allocating any sequence,
and its batch skips any that commit afterwards. Entries an older replica staged,
or that were staged before an upgrade, therefore never reach `_smrt_changes`.
The single-argument `_smrt_drain_changes(limit)` remains as a compatibility
entry point for older replicas during a rollout. It delegates with no
exclusions, which is the old behaviour; its output stays covered by the read,
signal and retention refusals above. The bootstrap and raw-handle probes require
both overloads (and, since #5402, the status drain both delegate to; see the
probe states under Change Feed), so an upgraded database installs the new one
before current code calls it. A newly created two-argument drain inherits the compat drain's
reconciled EXECUTE grants, so a hardened ACL with no PUBLIC EXECUTE carries
over. The compat drain has its own exception boundary. The purge is bounded per
pass, like the sequencing batch.

In a permissions-managed deployment the migration owner installs the helpers
before current replicas boot. Permission plans must come from the current CLI:
an older planner reports the two-argument overload as an unsupported routine.

`pruneChangeFeed()` additionally deletes sensitive rows below the horizon on
every sweep, ahead of either retention bound, so credentials do not sit at rest
for the retention window. That deletes from the middle of the retained run,
which the age bound goes to lengths to avoid — permissible only because these
rows are unservable on every read path, so no page ever contained them and no
cursor can fall into the gap. It **does** move `floor`, and usually will: a
session is created before the first domain write and re-saved on every request,
so the lowest retained sequences are typically credential rows. `floor` is read
live (`MIN(seq)`) on every `getChangesSince` and never cached, so the only
consequence is that a cursor below the new floor is answered `resyncRequired`
and refetches — including a `since=0` client on a never-pruned feed. Extra
resyncs, never a missed change. The horizon does not move, because the newest
entry is retained even when it is sensitive; that preserves "a non-empty feed
is never emptied" and means one credential row can linger until the next write
moves the horizon past it.

Because a non-observable table appends nothing, it also has no ETag source:
`getTableVersion()` would pin at whatever an older build last wrote and then
fall back to the global horizon, which moves only on unrelated traffic — so a
conditional GET could answer `304` for a revoked API key or a rotated session.
`getTableVersion()` therefore returns a deliberately **unrepeatable** value for
such a table — 48 bits of `crypto` randomness per call, not a per-process
counter, because two replicas' clock-seeded counters drift through each other
and the ETag carries no per-process entropy — so no *concrete* `If-None-Match`
can match and every such read is a full 200. It is the single point every ETag
path goes through (the runtime `APIGenerator`, the generated
`conditionalVersionedRead`, and route files an older generator already
emitted), so no call site needs a special case. A wildcard `If-None-Match: *`
still 304s; the read paths evaluate it only after the payload is built, so it
distinguishes nothing an unconditional request would not.

STI sensitivity is table-wide. Manifest generation and registration refuse a
hierarchy mixing classes declaring `sensitive: true` with classes omitting it or
declaring false (`CONFIG_STI_MIXED_SENSITIVITY`, #3456). Mark every class sensitive
or put the sensitive and public models on separate tables. This preserves the
historical-read and live-signal protections without introducing a discriminator
into old feed rows. A uniformly sensitive hierarchy declares its shared table;
the authoritative write-path check still verifies the instance's actual table.

Scope note: the generated `_changes`/`_events` routes — both the SvelteKit
routes and the runtime REST generator's — authorize on an authenticated
principal plus tenant scoping (`getTenantScopedChangesSince`, fail-closed) by
default. A consumer-supplied table/row authorization seam beyond that —
`change-feed-authz.ts` (#3020, below) — is optional and off until registered.

## Consumer table/row authorization seam (#3020)

Tenant scoping keeps one tenant from seeing another's rows, but it cannot
express "table X is readable by some principals of the tenant but not others"
or "principal P only sees their own rows of table X" (e.g. a bay-tablet
station versus the back office). `?tables=` on `_changes` was always a
client-chosen filter, never enforcement — a table the client did not ask for
was withheld only because it did not ask, not because it could not have.

`src/change-feed-authz.ts` closes that gap with two independent, optional
hooks, dependency-inverted onto `globalThis` exactly like
`resolveDispatchTenantScope` (`dispatch/tenant-resolver.ts`), so a consumer
registers them once with no change to the generated "DO NOT EDIT" route files.
Both hooks are evaluated identically by **every** transport — the generated
SvelteKit `_changes`/`_events` routes AND the runtime REST generator's
`_changes`/`_events` (`generators/changes-route.ts`, `generators/events-route.ts`)
— so a consumer serving both cannot register a hook that protects one and
leaks through the other:

- `setChangeFeedAuthorizer(authorizeChangeFeed)` — table-level.
  `authorizeChangeFeed({ locals, request, tables }) => allowedTables` returns
  the tables the requester may read from the feed at all; the result is
  INTERSECTED with the client's `?tables=` filter (never unioned), so a table
  the hook does not name is never queried, let alone returned.
- `setChangeFeedEntryVisibility(isChangeFeedEntryVisible)` — row-level, for
  scope narrower than a whole table. Applied per entry, after the table
  filter, before anything is serialized — including a live `_events` signal.

`locals` is SvelteKit's `event.locals`; `request` is SvelteKit's
`event.request` or, on REST, the `authMiddleware`-processed `Request`. REST
has no `locals` concept, so REST routes pass `locals: undefined` and a
REST-hosting consumer identifies the principal from `request` instead
(whatever the `authMiddleware` attached — headers, a decoded token, etc.).
Every generated route supplies `request`.

Both hooks are optional and independent; unregistered, every transport
behaves exactly as before (tenant-scoped only). A hook that throws or returns
something other than the documented shape fails closed to "authorizes
nothing" for that call — same posture as a throwing `resolveDispatchTenantScope`
resolver, and the same 200-empty-page shape the sensitivity filter above
already gives a request naming only tables it may not see (never a 5xx, which
would tell a caller its own hook is broken — indistinguishable from "denied"
from the caller's side).

Every filter narrows the *returned* `changes`; nothing ever touches
`cursor`/`resyncRequired`/`resyncCursor` — mirrors the sensitivity filter's
"filters affect what is returned, never how the cursor advances" and for the
same reason: a client must advance past a denied entry without re-polling it
forever, and the entry's row id/timing must never be inferable from a stalled
cursor. Table denial sets `getChangesSince`'s explicit `denyAllTables: true`
option rather than passing an empty `tables` array, because `getChangesSince`
treats an omitted/empty `tables` as "no filter" and would otherwise widen the
read. `denyAllTables` skips the `table_name IN (...)` clause (and the query)
entirely — an earlier version instead passed a guaranteed-no-match sentinel
table name through that clause, which broke on PostgreSQL (it rejects a NUL
byte in a text parameter, turning a denied request into a 500 instead of the
required 200 empty page, #3020 P1 follow-up). `denyAllTables` still runs every
resync/pruned-cursor check unfiltered first, so the real horizon computation
runs and the cursor still advances — it just matches zero rows.
`change-feed-authz.ts`'s `isChangeFeedDenyAll()` is the one place that decides
"empty allow-list" (deny all) vs. "no hook registered" (no filter); both
`readAuthorized()` (pull side) and `buildChangeEventStream()`'s catch-up loop
(push side) call it rather than re-deriving the distinction. With NO hook
registered, `resolveAuthorizedChangeFeedTables()` normalizes an explicit empty
requested `tables: []` to `undefined` before that decision runs: `?tables=`
with nothing in it is documented as equivalent to an omitted filter, and
without a hook there is no authorized answer to narrow anything with — feeding
`[]` through unchanged would let `isChangeFeedDenyAll()` read it as "deny
every table" and silently break the promised unchanged default (#3020
follow-up). Once a hook IS registered, its own answer is what decides
deny-all, exactly as above.

A registered hook's returned table list is also validated for USABLE
strings, not just string-typed ones: any entry that is empty or contains a
NUL byte fails the whole call closed to `[]` (deny all), the same posture as
a non-array or non-string result. This closes the same NUL-byte hazard the
`denyAllTables` sentinel removal above fixed for a *synthesized* value — here
the NUL byte would come from the hook's OWN answer, which otherwise flows
straight into the ordinary `table_name IN (...)` clause and 500s on
PostgreSQL (#3020 Copilot follow-up).

`getAuthorizedChangesSince()` / `getAuthorizedTenantScopedChangesSince()` wrap
`getChangesSince()` / `getTenantScopedChangesSince()` with both hooks applied;
BOTH `_changes` routes (SvelteKit's `vite-plugin/changes-route.ts` and REST's
`generators/changes-route.ts` `handleChangesRoute`) call the tenant-scoped
variant, and `buildChangeEventStream()` (`change-signals.md`) — shared by
BOTH `_events` routes — applies the same hooks to catch-up replay and live
signal delivery, resolving the table allow-list ONCE at connection open
(mirrors captured tenant scope).

## Compatible bulk mutations (#2818)

`appendChanges(db, entries)` validates all inputs before writing and returns one
sequence (or PostgreSQL staged `null`) per entry in input order. A nonempty batch
uses one client SQL statement and one set-based insert. The PostgreSQL
`_smrt_append_changes(jsonb)` helper chooses the staged/direct path once before
its own writes assign a transaction ID, and retains the same exception isolation
as the single-row helper. Bootstrap refreshes its body marker and runtime grants
include this exact helper signature.

The registered feed interceptor explicitly supports grouped lifecycle completion.
`recordInstanceChanges()` retains observable-table filtering, row/tenant IDs,
per-row operations, and best-effort failure handling. It publishes each direct
sequence in order; staged entries publish through the existing committed drain.
A batch is never replaced with a table-level bump or a single aggregate event.
The junction caller bounds its batch; the low-level append API does not split
one logical append into partially committed chunks.

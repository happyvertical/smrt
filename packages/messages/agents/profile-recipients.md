# Protected external-contact email recipients

`enqueueEmail` accepts exactly one of the existing `recipientUserId` or new `recipientProfileId`. Profile recipients are **email only** and reference a real tenant-owned public `smrt-profiles:Profile`; they do not need an auth User. No address, sentinel User, inferred tenant membership or recipient array is accepted. The one public `Profile.email` scalar is normalized by public `normalizeIdentityEmail`; the host's `resolveProfileRecipient` must authorize and return exactly that same current address. Multiple alternative emails are never selected implicitly.

Use `profileNotificationPolicy('your.host-policy.v1')` as `requiredDispatchPolicy` and `kind = 'protected:' + policyId`. Register that exact trusted handler in `dispatchPolicies`, with immutable document/recipient binding. The reserved `profile:` policy namespace and `protected:profile:` kind force profile identity in saves, enqueue, leasing and canonical send. Changing/clearing kind, either identity, address or policy on an existing protected row or natural-key clone is denied. A trusted application inventing a completely separate ordinary event has a distinct identity and is outside the clone threat model.

The host must check the real resource relationship (for example issued Invoice → Customer.profileId and current Project → Client.contactProfileId), current actor/privacy/field grants and contact authority at preview, approval and every policy handoff. Generic tenancy alone cannot grant that relationship. The service also re-resolves the tenant-owned profile and host callback before leasing and immediately before provider transport, denying changed/deleted/foreign/unrelated contacts. Broad dispatch without the matching protected handler stays blocked with no attempt or provider call. Existing Message/EmailSender protected canonical checks cover profile sends too. Unknown outcomes remain uncertain until reconciliation; this API adds no resend shortcut.

Legacy User inputs and `resolveRecipient` are unchanged. `NotificationSuppressionRequest` and existing `optOutSuppression` retain their required User ID and exact legacy TypeScript contract. Profiles use the separate optional `isProfileSuppressed(NotificationProfileSuppressionRequest)` hook, checked at enqueue and dispatch. It receives a real Profile ID and no User ID; a host supplies its current contact opt-out/resource policy. User opt-out preferences are never inferred onto unrelated external contacts. No global User opt-out row is fabricated.

## Explicit schema maintenance

Inspect `planNotificationProfileRecipients(db, 'postgres' | 'sqlite')` first. It is read-only, returning SQL, unexpected invalid/duplicate row IDs and obsolete index inventory. On an existing PostgreSQL database, apply this explicit maintenance **before** the normal PostgreSQL-safe manifest migration: the expanded NULL-equal conflict key requires an atomic writer window and cannot be created by concurrent-index DDL. Then run normal manifest migration and verify the helper's empty replay. On a fresh database, create the normal manifest schema first, then apply this helper to install the physical typed CHECK.

`migrateNotificationProfileRecipients` runs a fresh plan inside one transaction; PostgreSQL takes an exclusive table lock. It never performs runtime auto-DDL. The caller must use a root migration handle in an authorized writer maintenance window. The same public helper supports the legacy-table-first path; do not disable PostgreSQL-safe mode globally to get past its maintenance refusal.

The migration preserves all legacy row IDs, User references, message/provider IDs, outcome/history and existing data. Legacy rows become `recipientKind='user'` with actual NULL profile reference; profile rows require actual NULL User reference. User/profile unique indexes preserve logical idempotency independently. The expanded natural key `(tenant, kind, User, Profile, channel, sourceRef)` retains public raw-save/upsert semantics. PostgreSQL's obsolete four-column User-only `NULLS NOT DISTINCT` index is the **only** old index removed; otherwise it would collapse distinct profiles with the same source. Unexpected named index or CHECK drift and invalid/duplicate old identities require explicit reconciliation, never guessed repair.

SQLite uses public core `buildSqliteRebuildStatements` to preserve the live DDL, indexes, triggers, rowids and data while relaxing the unused User column, adding profile fields and a real table CHECK. It refuses incoming-FK rebuild shapes and never disables foreign keys. Unsupported/ambiguous schema shapes fail closed for an explicit maintenance path. A failed DDL step rolls back old schema/indexes/history; replay after success is empty.

Profile enqueue/dispatch verifies actual physical nullability, the complete CHECK predicate, required unique indexes and absence of the old four-column NND index. A migration ledger/version flag alone never opens this gate. Ordinary User use is not gated on the extra profile CHECK/index maintenance **after normal framework additive schema migration** has supplied the typed columns/defaults. A zero-new-column old database still needs that normal schema phase; this is not a claim that new ORM code writes old physical columns unchanged. The explicit helper also plans/applies from a legacy table directly during maintenance, preserving old rows. Mixed old binaries must be drained before migration/activation; old binaries cannot honor typed protected contracts. Follow released-package/schema adoption before enabling any real host.

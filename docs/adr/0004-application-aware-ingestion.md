# ADR 0004: application-aware ingestion

Status: proposed for contract review, 2026-10-08. Implements [#3669](https://github.com/happyvertical/smrt/issues/3669), contract gate for [#3668](https://github.com/happyvertical/smrt/issues/3668). Names below become frozen on merge; **none of the new APIs or tests are implemented by this ADR**.

## Decision and ownership

Create `@happyvertical/smrt-ingestion`: durable intake, evidence revisions, action proposals, review, execution accounting and explicit feedback. Assets own bytes and derivation; messages own transport identities; applications own semantic handlers, confidential access and content filtering. There is no new moderation/quarantine subsystem, model registry, generic workflow engine, or approval mechanism that supersedes a domain's approval API.

Use `receive → preserve → extract → interpret → propose → review → execute → observe`. Unknown, ambiguous, unsupported and retain-without-action are useful results. Generative extraction supplies candidate data, typed decisions evaluate bounded choices, and deterministic services enforce authority. Neither input text nor a model can select a principal, alter policy, approve work or invoke arbitrary tools.

## Records and identities

All ingestion rows require a non-null tenant UUID; every unique key includes tenant. Public models expose authorized list/get only. All writes go through `IngestionService` server methods; generated create/update/delete are disabled across REST/CLI/MCP. DTOs exclude storage credentials, internal errors and unauthorized evidence. JSON columns use guarded string accessors and `transformJSON()`.

| Record | Identity and immutable content | State and legal transitions |
| --- | --- | --- |
| `IntakeItem` | UUID; authenticated source ID/version, source delivery key, captured actor/delegation ceiling, confidential scope ID, retention policy version | Receipt: `reserved → preserving → ready`; preserving may enter `needs_attention`, then resume preserving. Ready is never undone by processing failure. Expiry changes visibility to `expired`, preserving a replay tombstone. |
| `IntakeEvidence` | UUID, item, immutable asset snapshot/hash/length or immutable message snapshot, source part ID, parent evidence, media type, source asset/message identity/version, page/time ranges | Append-only evidence version; derivatives point to originals, never replace them. Revocation/expiry removes access and cancels pending work. |
| `IntakeAnalysis` | Item + increasing input revision; immutable evidence IDs/hashes and processing configuration; current attempt ID and monotonic fence generation | State projects the current attempt. Retry preserves the input revision; changed inputs/configuration create a new revision. |
| `IntakeAnalysisAttempt` | UUID; unique `(tenantId, analysisId, attemptNumber)`; fence generation, worker/lease identity, timestamps, actual provider/model/prompt/catalog/policy versions, limits/usage, output refs/digest and safe errors | `queued → running → completed / partial / failed / needs_attention`; an active attempt can become `superseded`. Terminal provenance/output is immutable; retries append, never overwrite. |
| `IntakePlan` | UUID + revision; item, playbook/handler versions, definition hash, normalized input, ordered frozen step bindings and expansion digest | Non-executable grouping of step actions. Changed expansion creates a new revision and invalidates affected pending approvals; completed actions remain completed. |
| `IntakeAction` | Stable UUID minted once per intended business effect; item + action ID; durable execution identity independent of actor/job/token/digest | Projection: `proposed → waiting_review → authorized → executing → succeeded|failed|outcome_unknown`; reject/defer/supersede are review outcomes; rejected/deferred cannot execute. Failed can retry only with the same approved binding and live authorization. Unknown must reconcile. |
| `IntakeProposal` | Action + monotonically increasing revision; analysis/evidence refs, handler/operation version, canonical args, preview hash, target preconditions, dependency bindings | Immutable after publication. New edits append a revision and supersede the old before apply. A completed action cannot receive a new executable revision. |
| `IntakeReviewDecision` | UUID; reviewer from authenticated session, proposal revision/hash, decision, timestamp, reason, authorization/policy provenance, expiry | Immutable `approve|reject|defer|correct`; correction records changed values and creates a fresh proposal requiring review. CAS on the action's active proposal/review version admits one competing terminal decision. |
| `IntakeExecution` | Action + attempt; approved binding hash; current principal/policy audit, fencing token, result refs/digest, external idempotency key | `claimed → succeeded|failed|outcome_unknown`; success is immutable and replayable. A unique durable action completion prevents second effects. |
| `IntakeFeedback` | Explicit human judgment and decision provenance, corrected fields/destination, handler/evidence versions, access scope, supersedes ID | Append-only correction history; eligibility is computed live, never implied by analysis or execution success. |

Creating an analysis retry atomically allocates the next attempt number, increments the analysis fence, supersedes any active prior attempt and sets the current attempt ID. Completion must CAS both current attempt ID and fence before publishing output; a late provider response cannot publish or mutate a terminal attempt. Each proposal binds the exact completed/partial attempt ID and output digest as well as input revision. A replacement attempt cannot silently change reviewed evidence; adopting its output requires a new proposal/review.

Receipt dedupe key is `(tenantId, sourceId, deliveryKey)`, not a content hash. Same key with different authenticated scope or payload digest is a conflict, not an overwrite. Same bytes in two emails produce separate items. A re-analysis retains action IDs only for explicitly reconciled, unexecuted intentions; uncertain equivalence requires human resolution. Creating a *new* effect after success requires an explicit new action linked to the prior action, never silent reprocessing.

## Receipt recovery protocol

`SourceAdapter.receive` authenticates transport/account and produces `{sourceId, sourceVersion, deliveryKey, parts, sourceContext}`. The host resolves tenant, actor, confidentiality and enabled processing budget from trusted account/session configuration; supplied labels, sender claims and tenant fields cannot grant authority. Parts carry stable part IDs, bounded streams or existing owner references, declared media type and optional expected hash. Enforce actual byte/type limits while streaming.

1. Commit the unique reserved receipt and a storage intent per part, including a stable asset UUID/object key, expected length/hash when available and source replay locator. Do not acknowledge.
2. Persist each original under that recoverable key using assets' public store/storage resolver APIs. A retry reads/verifies an existing object instead of blindly overwriting it. Record actual hash/length and immutable URI/version in the evidence row. No network call holds a database transaction.
3. In one DB transaction, verify every required part is durable, mark receipt ready and insert a dispatch intent. A repair scan enqueues missing jobs from dispatch intents, and marks intents delivered idempotently. Workers dedupe by item/stage/revision, so a crash between enqueue and marking does not duplicate domain effects.
4. Only then return `{kind:'accepted'|'duplicate', itemId, receiptVersion}`. Source acknowledgement happens after this result. Transient failure returns `retry`; irrecoverable malformed input returns `rejected` with a safe category. Watch-folder files move to processed only after acceptance; email checkpoints advance only after all required attachments are snapshotted.

Recovery covers reservation-without-bytes (refetch/retry), bytes-without-evidence (verify stable key and adopt), evidence-without-ready (finish transaction), ready-without-job (repair), job-without-dispatch-mark (dedupe), and ready-without-source-ack (return original success). A fencing lease prevents concurrent preservers finalizing incompatible content. Orphan cleanup requires an expired intent and proof no evidence/retention hold references the object. Storage key selection must be recoverable before writing; #3670 must prove the existing resolver supports this or add a narrow public assets seam, not call private members.

Existing assets/messages are **snapshotted** into ingestion-retained originals by default, including message text, allowlisted non-secret headers and attachment relationships. Referencing a mutable remote URI alone is not preservation. A host may use a pinned immutable owner object only with a retention lease whose enforcement prevents mutation/deletion for the configured term. If unavailable, copy. Upstream deletion does not silently rewrite evidence; explicit privacy deletion revokes originals, derivatives, previews and feedback, leaves a minimal non-content replay tombstone, and blocks execution. The authenticated source must guarantee delivery-key uniqueness for the tombstone term; after configured replay expiry, reject old deliveries rather than run them anew. Operators cannot clear successful action tombstones while replay remains accepted.

## Public handler and service contracts

The following are normative contract shapes, not importable code. Qualified identities are `@scope/package:name`, with explicit immutable semantic version. Changing execution semantics requires a new version.

`IntakeHandler<Args, Result>` contains:

- `id`, `version`, business `description`, supported evidence kinds/MIME types, JSON-schema `argsSchema` (required fields, bounded strings/arrays, no unknown keys), and bounded `resultSchema`.
- A discriminated contract: a single-operation handler has `operation: {model, action, version}` and `execution`; a playbook handler has `operation: {playbookKey, definitionHash}` and `expand`, **never** `execution`. Resolve public `ObjectRegistry` metadata and `CapabilityDeclaration` (`effect`, `idempotent`, `openWorld`); undeclared capabilities fail closed. No second structural registry. The catalog is an explicit application-owned list of enabled semantic adapters.
- `candidates(input, context, {limit, cursor}) → {items, nextCursor?}`: hard maximum 20, query-length/time budget, stable opaque cursor scoped to actor/tenant/access/policy/catalog versions. Lookup uses authorized public domain collections. Filter before ranking or summarizing; no global fallback, hidden counts or existence disclosure.
- `preview(args, context) → {display, normalizedArgs, targetPreconditions, evidenceRefs, resultBindings}` and `validate(args, context) → {ok, fieldErrors}`. Both enforce read scope and have no domain side effects. Preview is deterministic for its binding; output is escaped data. Missing required data yields needs-information, not invented values.
- Single-operation handlers only: `execution: {kind:'database', apply(args, txContext) → Result}` or `{kind:'external', submit(args, context, idempotencyKey), reconcile(context, idempotencyKey)}`. A database handler receives the exact transaction-bound executor used by the ingestion ledger and must construct/rebind every collection/object from it. Separate connections, nested root transactions, detached jobs or network effects are forbidden in that mode. External reconciliation returns `succeeded(result)|not_applied|unknown`; only proven not-applied permits resubmission.

Context is server-created and contains authenticated actor, tenant, confidential access predicates, fresh principal run, captured ceiling, limits and evidence reader; it is never accepted as client JSON. `txContext.db` is the public SQL executor, not a replacement ORM. Catalog discovery, candidates and previews require the same access checks as original retrieval and apply.

`IngestionService` provides `receive`, `listItems`, `getItem`, `getEvidence`, `analyze`, `listHandlers`, `findCandidates`, `previewProposal`, `submitDecision`, `applyAction`, `reconcileAction`, `recordFeedback` and `proposeRule`. Inputs use IDs plus expected revision/binding hash; the server reloads authoritative rows. Mutations have request-id replay protection in addition to durable action identity. `submitDecision` takes decision/expected proposal and session CSRF/transport authentication, not a caller-supplied reviewer or permission list. `applyAction` takes action ID, never arbitrary handler arguments. Internal stage execution is not a generated public method. API/CLI/MCP adapters call this same service. Jobs continuations may collect missing data; they cannot manufacture `IntakeReviewDecision` approval. Replayed, forged, expired or wrong-session answers fail closed. A domain with its own approval API still requires that API; ingestion approval permits calling the approved operation, not bypassing its lifecycle.

## Policy and current authority

Resolve immutable application hard ceilings, then tenant restrictions, then source restrictions, then per-request restrictions. Every layer intersects handler/provider/reviewer/access/operation allowlists, takes minimum budgets and retention maxima, maximum required certainty, and ORs review requirements. A deny always wins; no lower layer re-enables an upper disable. Automation is absent by default and requires an explicit application eligibility rule, tenant opt-in and source opt-in, evaluated acceptance evidence and current operation eligibility. Unknown capability/policy versions require review or refusal. Content/model labels cannot supply these settings.

Review authority and execution authority are separate. A human must currently have access to the item/evidence and permission to approve the specific operation. Immediately before each action or playbook step, the host resolves live grants and current ownership/confidential scope, intersects them with the captured source/delegation ceiling and current narrowed policy, then constructs a **fresh** `executeAsPrincipal` context. Never reuse the analysis/reviewer run; `PrincipalRun.assertOperation` checks the run's published grants, not a fresh lookup. If freshness cannot be established, deny. Revocation after approval, evidence access loss, expiry, operation-version drift or a failed target precondition invalidates execution and requires new preview/review where repair is possible. Authorization and target CAS occur within the mutation boundary; a host must serialize/revalidate grant changes at that boundary or explicitly fail closed rather than promise instantaneous revocation it cannot enforce.

Approval binds canonical arguments, evidence hashes/analysis revision, handler and operation version, target identity/revision, dependency specification and preview digest. Policy-authorized automation records distinct machine authorization provenance; it never impersonates a human review. External/destructive/open-world actions stay review-required unless explicitly permitted and independently evaluated by the application.

## Dependencies, execution and partial outcomes

A playbook handler provides side-effect-free deterministic `expand(normalizedArgs, resolvedDefinition) → {steps}`. The service resolves the pinned definition on the server through the current narrowed policy. Each returned step is `{stepIndex, handlerId, handlerVersion, args, resultBindings}`: exactly one entry per resolved operation step, in definition order, with a single-operation handler whose declared model/action matches that step. `args` are concrete schema-validated values; `resultBindings` map declared argument fields to `{stepIndex, resultField, expectedModel}` from an earlier step. No expressions, runtime-selected handlers, nested plans or opaque whole-plan callback are permitted. Browser intent steps are unsupported by ingestion v1 and fail expansion closed.

Before publishing previews, one transaction persists `IntakePlan` and a stable step-index → action-ID mapping, creates each step's `IntakeProposal`, and translates result bindings into the action/revision references below. Expansion retries use the same plan/request identity and replay that mapping, never mint another effect. The frozen plan revision includes the resolved definition/handler versions, ordered step mapping, per-step normalized args/preview hashes/preconditions, result dependencies and `onStepFailure`; its digest is bound by every step approval. Each step is reviewed and authorized individually. Edits re-expand into a new plan revision, retaining existing action IDs for the same steps; changed bindings invalidate pending approvals, and completed step bindings stay pinned to their original proposal/result: an edit that changes one is rejected, never replaced or re-executed implicitly. Execute in declared order through the existing per-action executor. `abort` stops later steps after failure; `continue` permits only independently satisfied steps, never a dependent step without its approved predecessor result. Plan status aggregates step outcomes; it is not an execution ledger or authority grant.

A proposal can refer to a predecessor only with `{actionId, proposalRevision, resultField, expectedModel}`; arbitrary expressions and cross-item references are prohibited. The catalog result schema allowlists fields (initially only record IDs). Reject cycles and missing/failed prerequisites. A plan is an acyclic set of actions, not an atomic workflow.

For “create draft then attach”, review explicitly displays a symbolic target “the ContentDocument created by action A revision 1”, the predecessor's complete approved preview and the exact asset/relationship. The dependency approval binds that specification, not a wildcard target. Upon A success, persist and hash its typed result, verify tenant/model/ownership and bind B's resolved target to that immutable result. This authorized substitution does not require another review when it exactly matches the reviewed binding. Any changed upstream revision, result digest, target type/owner or material state invalidates B and requires fresh preview/review. A result cannot be replaced after success; reconciliation must recover the same committed result. Existing-target attachments always bind a concrete target revision.

Database apply claims/fences the durable action, verifies the current approval and target revision, writes through public domain APIs, and commits effect + execution result + action success in the **same transaction**. Rollback leaves no business effect or completion. Workers lock/CAS the durable action, not a process mutex. `runOnce` may wrap transport retries but its actor/token/content key and retention are not business identity. Changing reviewers or arguments cannot duplicate a completed action. Terminal results survive job/runOnce cleanup; expired payload retention retains a safe success/tombstone replay.

External apply durably records an attempt/idempotency key before sending. A crash/timeout after send becomes outcome_unknown. Reconciliation precedes retry; a provider without a reliable key or lookup remains needs-attention for human resolution, never guessed safe. Each playbook step has its own stable action identity, current authorization and persisted progress. Successful predecessors remain successful if a later step fails; retry only the failed step, and do not claim compensation or all-or-nothing behavior.

## Extraction adapter

`ExtractionAdapter.extract({evidence, limits, signal}) → ExtractionResult` returns provider/model/version (explicit `unknown` when unavailable), input hashes, observed capabilities, ordered segments and `complete|partial|failed|unsupported`. A segment contains text plus actual page/batch bounds or transcript start/end milliseconds; fine-grained boxes and confidence are optional **only when advertised and measured**. Capability metadata records confidence scale/calibration provenance and location granularity. Keep extraction confidence, routing probability, match certainty and action risk separate; none is approval.

Result includes truncation flags, omitted ranges, token/byte/page/audio/time/cost usage and safe categorized errors (`unsupported_type`, `malformed_output`, `limit`, `timeout`, `unavailable`, `authentication`, `cancelled`, `integrity`). Partial output is reviewable with warnings; it cannot satisfy rules requiring complete evidence. Missing confidence is unknown, not zero or one. Reject unknown status values and malformed ranges; preserve safe provider provenance without raw secrets/errors.

Use existing PDF embedded text/rendering/OCR, existing image OCR/vision and speech transcription. Unlimited-OCR declares no confidence or boxes; discard its synthetic 100 as a confidence measurement and retain page/batch provenance. #3672 must prove a real multipage TIFF decode-to-supported-image route with bounded memory/pages and original-page mapping, or a currently supported configured provider. Do not advertise TIFF as supported merely because fax is a source. Verify capabilities before requesting an SDK-owner fix; no replacement extraction stack is authorized. #3671 retrieves and persists email attachment bytes explicitly: `EmailAccount.syncFrom` currently records hasAttachments without doing that work.

## Learning and retention

`recordFeedback` distinguishes interpretation correctness, approval choice and observed execution outcome. Only explicit reviewer correctness/correction judgments become retrieval examples. Agent run completion/success is not a label; leave the agent learning default disabled for ingestion unless an adapter supplies this exact labeling contract. Retrieve tenant- and confidential-scope-accessible examples only; recheck access at retrieval, not just embedding time. Version examples by handler/evidence/prompt; superseded, deleted, revoked or stale-incompatible examples are excluded. Human corrections dominate retrieved suggestions. Rule suggestions carry evidence, expected impact and policy version; a separately authorized policy owner adopts them explicitly. Adoption cannot widen a captured authority ceiling or change existing approvals. Retention deletes derived indexes and caches with originals, retains only necessary non-content audit/replay identity, and never creates cross-tenant learning.

## Worked examples

**Email bundle.** Account X authenticates tenant T; delivery E contains request text, invoice PDF and two photos. Reserve item I and four evidence parts (message parent plus attachment children); crash after the PDF write is recovered by its stable key. Ack only after all originals and dispatch intent commit. Analysis I/1 cites message/attachment hashes; absent OCR confidence stays absent. Propose A/1 to create a draft ContentDocument summarizing the request and B/1 to attach the invoice to A's typed result; photos remain independently unresolved. Reviewer R can read every part and approve both previews, explicitly including B's symbolic target. Another reviewer's stale rejection loses CAS. Fresh executor grants permit A; its result commits once. B fails and rolls back its join; A remains succeeded. A retry after restart/reviewer change returns A's original ID and applies B exactly once, only if current scope still allows it. If scope was revoked, B remains blocked. R corrects the invoice classification in feedback; that is a correctness label, whereas A's successful save is only execution telemetry. A later re-analysis creates I/2 but cannot create A again.

**Multi-document scan.** A watch-folder PDF/TIFF delivery is retained as one original. Extraction records pages 1–6 without prematurely making six business records. Analysis proposes logical documents pages 1–2, 3–5, and unreadable page 6, with two draft actions and an abstention. A human changes the split to pages 1–3 and 4–5: analysis/proposal revision 2 supersedes revision 1, old approvals cannot execute. Derived renditions cite original hash and exact page ranges. Approve the first draft; defer the second for missing fields. Restart releases no waiting worker. First draft succeeds; linking its evidence is denied after target revision change, requiring a new preview. Rejected guesses never become positive examples; corrected split/destination can. An incomplete TIFF conversion remains partial/needs-attention, never silently drops pages or auto-approves.

## Package graph, rollout and reference proof

`ingestion/models → core + tenancy + types`; `ingestion/server → models + assets + messages + jobs + agents + playbooks + PDF/OCR/speech/AI SDKs`; `/svelte → browser-safe DTOs + smrt-ui`. Domain packages do not depend on ingestion for their existing operations. The maintained consumer at `packages/ingestion/reference/` composes ingestion and content through explicit application handlers; content is a dev dependency of ingestion only. Use package dependencies, not inter-SMRT peers. Root/model exports must not re-export Node providers, filesystem/credential adapters or Svelte components. Browser DTO import smoke tests inspect the built dependency graph.

Initial server support: repository Node (currently >=26), SQLite and PostgreSQL. DuckDB, JSON persistence, edge runtimes and browser execution are not declared supported for ingestion v1 and must fail capability checks rather than silently weaken transactions. Browser review supports the maintained Chromium suite. Register migrations before runtime start; never create application tables during receipt/apply. #3670 owns models, exports, migrations, manifest parity and package scripts; later children coordinate changes through that owner.

Reference handlers (both application-owned, version 1):

| Handler | Concrete public seam | Required validation |
| --- | --- | --- |
| `@happyvertical/smrt-ingestion-reference:create-draft` | `Contents.create({db: tx})`, then collection `create` with `_meta_type: '@happyvertical/smrt-content:ContentDocument'`, explicit tenant, title/body and `status: 'draft'`; collection `create` already saves. Returns `{contentId}`. | Bounded title/body, allowed subtype, explicit non-null tenant; no publication, email send or global content. Effect and ledger must roll back together. |

These operations are real domain APIs, but the reference permission wrapper and capability declarations are new work in #3674. Content's existing governance remains authoritative; this reference creates drafts only and adds no content filtering policy. Public `withDatabase(db, callback)` is available when rebinding an existing object; never use a shared bound instance concurrently. `Content.addAsset` creates its join collection from `this.db`, a verified executor propagation seam.

Dependency order: #3669 reviewed/merged → #3670 → #3671/#3672/#3674 (disjoint files); #3673 follows durable records and extraction; **as soon as these compose**, run upload → real PDF extraction → proposal → authenticated approval → one draft domain result with crash/retry and tenant-denial cases. Deliver attach-evidence and dependency proof before final acceptance. #3675 expands review surfaces, #3676 adds feedback, #3677 runs broad integration/evaluation and adoption. #3677 is not the first exercise of domain execution.

Adoption guide outline: migrate and verify parity; configure storage/retention and authenticated sources; register application handlers/capabilities; configure live principal and confidential access resolvers; set provider residency/budgets; run the reference proof; mount service-backed inbox/review; operate repair/reconciliation and deletion; evaluate held-out data before enabling any automation. Production consumer, volume and retention periods remain owner configuration, not framework guesses.

## Evaluation contract and validation

Before fitting prompts, freeze a versioned synthetic corpus manifest with source hashes, labels, annotator/adjudication provenance and train/development/held-out partitions (60/20/20), grouped by originating conversation/document template so near duplicates never cross partitions. Include all media types, ambiguous destinations, missing fields, unknown handlers, hostile instructions, confidential scopes and provider failures. Minimum held-out: 100 actionable draft cases, 100 attachment cases and 100 abstain/unsafe cases; report exact denominators and confidence intervals, not just averages.

Pre-registered reference acceptance: draft routing precision >=95%, required-field exact match >=95%; attachment target precision >=99%; both actions recall >=80% on supported actionable cases; >=95% abstention on ambiguous/unsupported/unsafe cases; zero authority violations, unauthorized data disclosures, duplicate effects or false automatic effects. Human review is mandatory for both reference actions in v1. Automation acceptance is **not established** by these sample sizes: it stays disabled. A future per-action opt-in must pre-register a harm bound, confidence level, sample-size calculation and policy before evaluation; no post-hoc threshold tuning on held-out data. Report correction effort, abstention on supported cases, p50/p95 latency, per-item cost and provider/fallback failure rate. A failed accuracy gate blocks that handler's supported reference claim, not a forced nearest-category fallback.

The [behavior matrix](../test-matrix/3669-ingestion-contract.md) freezes future commands and coverage obligations. This ADR changes no runtime and claims no executed runtime or accuracy evidence.
